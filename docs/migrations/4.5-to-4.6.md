# FrontComposer 4.5 to 4.6 Migration

Use this guide when upgrading a `4.5.x` host that renders `FrontComposerShell`. FrontComposer 4.6
keeps the existing Shell component entry points, but generated lifecycle record constructors and
`Deconstruct` members change, so compiled consumers of those records must be rebuilt. The shell
now owns Module routing, route focus, and a fixed set of header controls. Hosts that customized
the header, relied on the Shell's root page, or registered Module names that are not a single URL
segment must adjust.

## Affected Versions

The changes apply to hosts moving from `4.5.x` to `4.6.0`. Check each item that matches your host.

| Change in 4.6 | Who is affected | What to do |
|---|---|---|
| `FcHomeRouteView` maps only `/home`; the Shell no longer serves `/`. | Hosts that relied on the Shell's root Home page. | Declare your own `/` page. It can render `<FcHomeDirectory />`. The account menu still returns to `/` after sign-in and sign-out. |
| The Shell supplies `/home`, `/{Module}`, `/{Module}/overview`, and `/{Module}/{Tab}`. | Every host. | Add `typeof(FrontComposerShell).Assembly` to the router's `AdditionalAssemblies` and to `MapRazorComponents(...).AddAdditionalAssemblies(...)`. Do not redeclare those routes. Follow the router contract in [FrontComposerShell](../reference/components/front-composer-shell.md). |
| `HeaderStart` no longer replaces the hamburger toggle. | Hosts that put `FcHamburgerToggle` inside `HeaderStart` to keep it. | Remove your `FcHamburgerToggle`; the shell always renders one before `HeaderStart`. |
| `ShowAccountMenu` is a compatibility parameter; the account menu always renders. | Hosts that set `ShowAccountMenu="false"` because they had no sign-in endpoints. | Map the authentication challenge and sign-out endpoints the account menu links to. |
| Module registration rejects unusable routes with `HFC1601` at startup. | Bounded contexts containing spaces, dots, or other URL characters; names that differ only by case; the reserved names `home`, `commands`, and `__frontcomposer`; names in `FrontComposerRouteOptions.ReservedSegments`. | Rename the bounded context to one route-safe segment: an ASCII letter or digit, then letters, digits, hyphens, or underscores. |
| Shift is not a modifier for single non-letter keys. | Shortcut registrations such as `shift+/` or `ctrl+shift+?`. | No action is required: `ShortcutBinding.Normalize` drops that Shift, so `shift+/` registers as `/` and works on every keyboard layout. Register the typed character in new code. |
| Selecting a Module rail tile opens its Module landing (`/{module}`). | Hosts or tests that expected the tile to open its projection flyout. | Use the tile's More menu for secondary destinations. |

Test harnesses that render `FcPageTabs` outside `AddHexalithFrontComposer` must also register
`NavigationFailureNotifier` and localization, because route-backed tabs report fallback and
navigation status through it.

## Why This Changed

Story 13.2 makes shell navigation deterministic. Each bounded context appears as one Module with a
default tab at `/{module}`, and a successful navigation focuses the destination's heading only
after it renders. That requires one route per Module name, a shell-owned router contract, and
header controls that adopters cannot remove, so keyboard and screen-reader users can always reach
navigation and their account.

## Old Code

```csharp no-compile reason="Illustrative 4.5 host registration and shortcut."
// Program.cs (4.5)
app.MapRazorComponents<App>()
    .AddInteractiveServerRenderMode();

// A bounded context with a space no longer maps to a single route segment.
[BoundedContext("Sales Orders")]
public sealed partial class OrderProjection { }

shortcuts.Register("shift+/", "HelpShortcutDescription", ShowHelpAsync);
```

## New Code

```csharp no-compile reason="Illustrative 4.6 host registration and shortcut."
// Program.cs (4.6)
app.MapRazorComponents<App>()
    .AddInteractiveServerRenderMode()
    .AddAdditionalAssemblies(typeof(FrontComposerShell).Assembly);

// One route-safe segment: the Module lives at /salesorders.
[BoundedContext("SalesOrders")]
public sealed partial class OrderProjection { }

shortcuts.Register("/", "HelpShortcutDescription", ShowHelpAsync);
```

Add the same Shell assembly to the router's `AdditionalAssemblies`. Mount `FcRouteFocus` after the
routed content, and wrap it in the `data-fc-route-content` container described in the component
reference.

## Analyzer And Code Fix

`HFC1601` reports an invalid Module registration at startup, before the shell renders. The
[HFC1601](../diagnostics/HFC1601.md) page lists the segment, uniqueness, reserved-name, and
canonical-alias rules. No code fix is available: rename the bounded context, or remove the host
route that collides with it, and rebuild. The other changes have no diagnostic; follow the table
above.

## Skill Corpus Evidence

The published FrontComposer skill corpus is unchanged. None of its examples customize
`HeaderStart`, set `ShowAccountMenu`, rely on the Shell's root page, or register a `shift+`
non-letter shortcut.

## Generated Command Form Changes

Story 13.3 changes the markup and behavior of generated command forms so focus, input, and
announcements survive validation, rejection, authorization, and concurrent-submit outcomes. 4.6
adds public API and replaces the synthesized constructor and `Deconstruct` members of generated
positional lifecycle records. Source constructor calls continue to compile because the new trailing
parameter has a default, but previously compiled consumers must be rebuilt and positional
deconstruction source must accept the added element. Hosts that style or test generated forms
through their old markup must also adjust.

4.6 adds this public API:

- The `FcValidationSummary`, `FcCommandBlockedOutcome`, and `FcValidationFieldDescriptor` types
  and the `FcValidationSummaryKind` enum in `Hexalith.FrontComposer.Shell.Components.Forms`.
- `CommandRejectedException.FromProblem` and `CommandRejectedException.Problem`.
- `ServerValidationApplicator.ApplyRejection`, which returns the new
  `ServerValidationApplicationResult`.
- The `FcLifecycleWrapper.MappedRejection` and `FcLifecycleWrapper.DisplayLabel` parameters, and the
  `FcPageHeader.IsCommandFormHeading` parameter.
- The `OnBlockedSubmission` parameter on every generated form.
- The optional `ProjectionFieldGroupAttribute.Description` property for command-form group help text.
- A trailing `HasMappedFieldErrors` positional member, defaulting to `false`, on each generated
  `RejectedAction` record and generated lifecycle state record. Existing constructor calls still
  compile. Code that deconstructs these records positionally must add the new element.

| Change in 4.6 | Who is affected | What to do |
|---|---|---|
| Generated command inputs are Fluent UI V5 editors (for example `fluent-text-input`, and the Fluent switch, select, and date picker) inside `div.fc-command-field`. The native `label` and `input.fc-command-input` elements and the `.fc-command-field-label` and `.fc-command-field-message` hooks are gone. A nullable enum property's select shows no chosen option while its value is null. | Hosts whose CSS, specimens, or tests target the removed native markup or class hooks. | Target the Fluent editor inside `div.fc-command-field`, or query editors by their accessible label. Style editors through Fluent parameters and tokens. |
| The `FluentValidationSummary` inside a "Validation failed" message bar is replaced by the focused, linked `FcValidationSummary` (`data-testid="fc-validation-summary"`). Generated forms also carry `novalidate`, so the browser no longer blocks a submit with its own constraint-validation messages, and the summary reports every client error. | Tests or styles that look for the old message bar or summary, or that expect the browser's own validation messages. | Assert the new summary, its linked entries, and the focus move after a failed submit. |
| The submit button is no longer disabled while a command is in flight. A later press dispatches nothing and announces "This command did not run. Another command is already in progress." once, in a status line inside the form. That status replaces the "Command already in progress" message bar that a blocked submit used to show. | Tests that expected a disabled submit button during a command, or the blocked-submit message bar. | Assert that no second dispatch happens and that the blocked status is announced, instead of checking `disabled` or looking for the old message bar. |
| The `CommandAlreadyInProgressTitle`, `CommandAlreadyInProgressAdmissionMessage`, and `CommandAlreadyInProgressPendingMessage` Shell resource keys were removed. | Hosts that override or read those keys. | Use `CommandBlockedTitle` and `CommandBlockedMessage`. |
| Generated forms expose a new `OnBlockedSubmission` parameter. | Custom renderers that host a generated form they hide, such as a zero-field inline trigger. | Bind it to show the blocked-submit outcome beside your visible trigger. Leave it unbound when the form is visible. |
| `FcFormAbandonmentGuard` wraps its `ChildContent` in an extra `div`. | Hosts whose CSS uses child combinators across the guard. | Update the selectors to allow the added wrapper. |
| Command properties that share a `[ProjectionFieldGroup]` name render in one `fieldset` whose legend is the group name. The fieldset sits at the group's first member and holds every member in declared order, so an ungrouped property declared between two members of a group renders after that group. An optional `Description` renders once as Fluent help text and describes the fieldset through `aria-describedby`. The first non-empty declared group description is used, even when that member's editor is hidden. | Commands that annotate properties with `[ProjectionFieldGroup]`. | Review the grouped layout. Use `[ProjectionFieldGroup("Change details", Description = "Identify the record and explain the change.")]` to describe the group. Declare each group's members next to each other, or remove the attribute from command properties that should stay ungrouped. |
| An authorization denial or sign-in requirement renders as a `FluentCard` holding `section[data-fc-authorization-denied="true"]`, with a focusable `h2` heading, instead of a `FluentMessageBar`. | Hosts whose CSS, specimens, or tests target the old denial message bar. | Target the denial card's `section[data-fc-authorization-denied]` and its heading. |
| A server `403` on any generated form, including a form without an authorization policy, now replaces the form's fields with the denial card. The card's heading and body use the Shell's localized denial copy (`UnauthorizedCommandWarningTitle` and `UnauthorizedCommandWarningMessage`); the server's problem title and detail are no longer shown. The fields return when the form is reopened, or when a later authorization check allows a policy-gated form. | Tests or hosts that expected the fields and a warning bar to stay after a `403`, or that match the server's problem text. | Assert the denial card and its focused heading instead of the fields, and read the expected copy from the Shell resources. |
| The form-abandonment warning renders as a `FluentCard` holding `section[data-testid="fc-form-abandonment-warning"]`, instead of a `FluentMessageBar`. | Hosts whose CSS or tests target the old warning message bar. | Target the warning by its test id, or its Stay and Leave buttons by their accessible names. |
| The unmapped rejection bar adds "Edit and retry", "Return", and "Copy support reference" actions. Its detail labels are localized, and "Docs code" became "Documentation code". | Tests that count the bar's buttons or match its English labels. | Update the expected actions and labels, or read them from the Shell resources. |
| A `409` rejection whose problem details map an error to an allowlisted field that the form renders shows a focused "Command rejected" linked summary, the field's inline error, and a `[data-testid="fc-rejected-mapped"]` card. The card's "Dismiss" action withdraws it and keeps the entered values and field errors. It no longer shows the rejection bar or announces "Submission rejected". | Tests or hosts that expect the rejection bar or its announcement for a field-mapped `409`. | Assert the linked summary, the inline field error, and `fc-rejected-mapped` for field-mapped rejections. Rejections without a mapped rendered field keep the rejection bar. |
| `[Description]` and `[Display(Description = ...)]` on command properties render as visible help text under the generated editor (`.fc-command-field-description`), and the editor is described by it. | Commands whose property descriptions were written only for tooling, such as MCP manifests. | Reword descriptions so they read as operator help text, or remove them from properties that should show none. |
| While a command is in flight, the lifecycle wrapper renders a visually hidden `h2` (`[data-fc-lifecycle-heading]`) above the form. It becomes visible only while it holds focus after "View active command". | Tests that count headings, or CSS that styles every `h2` inside a command form. | Exclude `[data-fc-lifecycle-heading]` from heading counts and broad `h2` selectors. |
| A destructive generated command reserves the single modal slot while its confirmation is prepared and shown. Activated from inside another modal dialog, or while another modal launch holds the slot, it is refused and dispatches nothing; before 4.6 its confirmation opened on top. While a confirmation holds the slot, the command palette, settings, and their keyboard shortcuts are refused too. | Hosts that trigger destructive commands from inside their own modal dialogs, and tests that open the palette or settings while a confirmation is pending. | Trigger destructive commands outside other modal dialogs, and close a pending confirmation before opening the palette or settings. |
| The destructive confirmation dialog takes its default title, body, and Cancel label from the Shell resources (`DestructiveConfirmationTitleTemplate`, `DestructiveConfirmationDefaultBody`, and `DestructiveConfirmationCancel`), and Tab and Shift+Tab stay inside the dialog. | Tests that match the old English literals, or that expect Tab to leave the dialog. | Read the expected copy from the Shell resources, and keep keyboard tests inside the dialog. |
| The public `FcLifecycleWrapper`, `FcFormAbandonmentGuard`, and `FcDestructiveConfirmationDialog` components now inject `IJSRuntime` and `IStringLocalizer<FcShellResources>`. Generated command forms now inject `IJSRuntime` too, and after rendering they import `_content/Hexalith.FrontComposer.Shell/js/fc-focus.js` to keep each editor's validation relationships on its focusable control. | Hosts and bUnit tests that render these components or generated forms directly without the FrontComposer service registrations. | Register localization, for example with `services.AddLocalization()`, and a JS runtime (bUnit supplies one), or use `AddHexalithFrontComposerQuickstart()`. bUnit's default strict JS interop rejects the unplanned `fc-focus.js` import: use loose mode, which `Hexalith.FrontComposer.Testing` sets by default, or plan that module's calls. |
| Thirty Shell resource keys are added for validation summaries, blocked submits, the active-command heading, rejection recovery, destructive confirmation, and form abandonment, with English and French values. | Hosts that ship their own culture resources for `FcShellResources`. | Translate the new keys. Until then, those cultures fall back to the English values. |
| A `bool?` command property's switch shows its validation error only in the linked summary, not as an inline field message, because the Fluent switch ignores `ValidationFieldFor`. | Commands that validate `bool?` properties. | Rely on the linked summary for those fields until an inline message is supported. |

None of these changes has a diagnostic or a code fix.
