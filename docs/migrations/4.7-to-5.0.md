# FrontComposer 4.7 to 5.0 Migration

Use this guide when upgrading a `4.7.x` host that maps MCP endpoints with `MapFrontComposerMcp`.
FrontComposer 5.0 makes the MCP authentication requirement impossible to remove with an appended
policy, ships an authentication scheme for `FrontComposerMcpOptions.ApiKeys`, and checks the host's
authentication and authorization services when it maps the endpoints. No public API is removed,
but host composition changes, so 5.0 is a major release.

This is a `manual-only` package/API upgrade. The CLI does not execute this version edge;
review the reference, namespace, and source changes below manually.

## Affected Versions

The changes apply to `Hexalith.FrontComposer.Mcp` hosts moving from `4.7.x` to `5.0.0`. Hosts that
do not map FrontComposer MCP endpoints are unaffected. If you are still on `4.5.x`, first read the
MCP host composition section of the [4.5 to 4.6 guide](4.5-to-4.6.md).

| Change in 5.0 | Who is affected | What to do |
|---|---|---|
| `MapFrontComposerMcp` attaches one authorization policy object to every mapped MCP endpoint: the host's default policy, from `IAuthorizationPolicyProvider.GetDefaultPolicyAsync()`, combined with `RequireAuthenticatedUser()`. It replaces the empty `RequireAuthorization()` of 4.6 and 4.7. ASP.NET Core requires every policy on an endpoint, so an appended policy adds requirements and cannot remove this one. An anonymous caller gets the authenticating scheme's challenge on every mapped endpoint: `401` for the API-key and bearer schemes, a redirect for cookie and OpenID Connect schemes. | Hosts that appended an `AuthorizationPolicy` object, such as a network or loopback assertion, and relied on it to admit anonymous callers. | Give those callers a principal, for example an API key from `AddFrontComposerMcpApiKey()`. `AllowAnonymous()` on the returned builder is the endpoint-level opt-out. Host code can also bypass the requirement, for example with an `IAuthorizationHandler` that succeeds `DenyAnonymousAuthorizationRequirement`, a custom `IPolicyEvaluator` or `IAuthorizationMiddlewareResultHandler`, or a convention that removes the authorization metadata. Each is a host-owned bypass that FrontComposer neither detects nor supports. |
| The default policy is read once, when `MapFrontComposerMcp` runs. | Hosts that change the default policy after mapping, or use a custom `IAuthorizationPolicyProvider` whose default policy varies per request. | Configure `AuthorizationOptions.DefaultPolicy` before mapping. Express per-request rules as a named policy or as requirements inside a policy you append. |
| `AuthenticationBuilder.AddFrontComposerMcpApiKey(string authenticationScheme = FrontComposerMcpAuthenticationDefaults.ApiKeyScheme)` authenticates the keys in `FrontComposerMcpOptions.ApiKeys`, read from the header named by `ApiKeyHeaderName`, before authorization runs. A matched key produces a principal with `TenantId` and `UserId` claims whose authentication type is the scheme name. A missing header yields no result; a multi-valued, blank, or unknown key fails with a fixed message that never contains the key. | API-key-only hosts, which got `401` for every request on 4.6 and 4.7, and hosts that wrote their own scheme to work around that. | Delete your own key-checking scheme. When MCP is the host's only authentication, make the scheme the default with `AddAuthentication(FrontComposerMcpAuthenticationDefaults.ApiKeyScheme).AddFrontComposerMcpApiKey()`. When the host has other authentication, scope the scheme to the MCP endpoints instead of making it the app-wide default: append `new AuthorizationPolicyBuilder(FrontComposerMcpAuthenticationDefaults.ApiKeyScheme).RequireAuthenticatedUser().Build()` to the builder that `MapFrontComposerMcp` returns. Listing both schemes in the default policy's authentication schemes is the alternative. |
| When the API-key header matches, the MCP handler refuses the request if the request's other authenticated claims carry a different tenant or user. On 4.7 the key's identity silently won. | Hosts whose default policy lists several schemes, so ASP.NET Core merges a bearer or cookie principal with the API-key principal. | Send one credential per MCP request, or make sure both credentials name the same tenant and user. Scoping the API-key scheme to the MCP endpoints, as above, keeps the principals apart. |
| Mapping throws an `InvalidOperationException` when `IAuthorizationPolicyProvider` or `IAuthenticationSchemeProvider` is not registered. The message names the missing `AddAuthorization` or `AddAuthentication` call. The check runs after the allow-all gate checks. It verifies the service registrations only, not that a default challenge scheme exists: without one, and without schemes on the policy, MCP requests still fail with `500`. | Hosts that map MCP without `AddAuthentication` or `AddAuthorization`. On 4.7 those hosts started and then failed every MCP request with `500`. | Register both services before mapping, and give the host a default scheme or name the schemes on the policy. |
| Development is detected with `IHostEnvironment.IsDevelopment()`, which ignores the case of the environment name. On 4.7 only the exact name `Development` skipped the allow-all gate rejection. | Hosts that run with an environment name such as `development` or `DEVELOPMENT` and relied on mapping to reject the allow-all sample gates. | Name every non-development environment explicitly, and register restrictive gates there. |
| The gates are resolved from an asynchronous service scope that mapping disposes through `DisposeAsync()` before it returns. | Gates with scoped dependencies that implement only `IAsyncDisposable`, which failed mapping on 4.7 outside Development. | No action. A gate whose constructor needs an active HTTP request still cannot be resolved at map time; move request-bound work into `IsVisibleAsync`. |

Two limits are unchanged in 5.0 and remain host responsibilities. Mapping rejects only the exact
`AllowAllMcpTenantToolGate` and `AllowAllResourceVisibilityGate` types, so a decorator that wraps
one passes the check. The SDK's own `MapMcp`, the stdio transport, and `McpServer.Create` skip every
FrontComposer host check; use `MapFrontComposerMcp` for HTTP hosting.

## Why This Changed

4.6 added an empty `RequireAuthorization()` to the MCP endpoints. An empty `[Authorize]` uses the
default authenticated-user policy only while no `AuthorizationPolicy` object is attached to the
endpoint. As soon as a host appended one, ASP.NET Core evaluated only the appended policy, so an
always-true or loopback policy let anonymous requests reach MCP dispatch. The guarantee that every
mapped endpoint requires authentication could be removed without a warning.

4.6 also enforced authorization before the MCP handler, while `FrontComposerMcpOptions.ApiKeys` was
matched only inside that handler. A host that authenticated agents only with API keys therefore
rejected every request with `401`, unless it duplicated the key check in its own authentication
scheme. The Counter sample did exactly that until 5.0.

5.0 folds the default policy and the authenticated-user requirement into one policy object, moves
API-key matching into an authentication scheme that uses the same hashed, fixed-time matcher, and
reports missing authentication services at startup instead of on every request.

## Old Code

```csharp no-compile reason="Illustrative 4.7 MCP host composition; the docs snippet project does not reference Hexalith.FrontComposer.Mcp."
// Program.cs (4.7)
string agentKey = builder.Configuration["Mcp:AgentKey"]!;

// A hand-written scheme that repeats the FrontComposerMcpOptions.ApiKeys check.
builder.Services.AddAuthentication(HostApiKeyHandler.SchemeName)
    .AddScheme<AuthenticationSchemeOptions, HostApiKeyHandler>(HostApiKeyHandler.SchemeName, _ => { });
builder.Services.AddAuthorization();
builder.Services.AddFrontComposerMcp(o =>
    o.ApiKeys[agentKey] = new FrontComposerMcpApiKeyIdentity("tenant-a", "agent-a"));

WebApplication app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();

// This appended policy object replaced the default authenticated-user policy, so anonymous
// requests from the same machine (loopback) reached MCP dispatch.
app.MapFrontComposerMcp()
    .RequireAuthorization(new AuthorizationPolicyBuilder()
        .RequireAssertion(context => context.Resource is HttpContext http
            && http.Connection.RemoteIpAddress is { } address
            && IPAddress.IsLoopback(address))
        .Build());
```

## New Code

```csharp no-compile reason="Illustrative 5.0 MCP host composition; the docs snippet project does not reference Hexalith.FrontComposer.Mcp."
// Program.cs (5.0)
using Hexalith.FrontComposer.Mcp;
using Hexalith.FrontComposer.Mcp.Extensions;

string agentKey = builder.Configuration["Mcp:AgentKey"]!;

builder.Services.AddAuthentication(FrontComposerMcpAuthenticationDefaults.ApiKeyScheme)
    .AddFrontComposerMcpApiKey();
builder.Services.AddAuthorization();
builder.Services.AddFrontComposerMcp(o =>
    o.ApiKeys[agentKey] = new FrontComposerMcpApiKeyIdentity("tenant-a", "agent-a"));

WebApplication app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();

// Every mapped MCP endpoint requires an authenticated caller. An appended policy, such as the
// loopback assertion above, now adds a requirement instead of replacing that one.
app.MapFrontComposerMcp()
    .RequireAuthorization(new AuthorizationPolicyBuilder()
        .RequireAssertion(context => context.Resource is HttpContext http
            && http.Connection.RemoteIpAddress is { } address
            && IPAddress.IsLoopback(address))
        .Build());
```

Delete the hand-written key-checking scheme. When the host keeps another default scheme, such as
JWT bearer, scope the API-key scheme to the MCP endpoints instead of making it the app-wide default:

```csharp no-compile reason="Illustrative 5.0 mixed-scheme host; the docs snippet project does not reference Hexalith.FrontComposer.Mcp or JWT bearer."
using Hexalith.FrontComposer.Mcp;
using Hexalith.FrontComposer.Mcp.Extensions;

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer()
    .AddFrontComposerMcpApiKey();
builder.Services.AddAuthorization();

// MCP endpoints authenticate with the API-key scheme only; the rest of the app keeps JWT bearer.
app.MapFrontComposerMcp()
    .RequireAuthorization(new AuthorizationPolicyBuilder(FrontComposerMcpAuthenticationDefaults.ApiKeyScheme)
        .RequireAuthenticatedUser()
        .Build());
```

Alternatively, let both schemes authenticate every endpoint through the default policy. MCP then
refuses a request whose bearer token and API key name different tenants or users:

```csharp no-compile reason="Illustrative 5.0 default-policy alternative; the docs snippet project does not reference Hexalith.FrontComposer.Mcp or JWT bearer."
builder.Services.AddAuthorization(o => o.DefaultPolicy = new AuthorizationPolicyBuilder(
        JwtBearerDefaults.AuthenticationScheme,
        FrontComposerMcpAuthenticationDefaults.ApiKeyScheme)
    .RequireAuthenticatedUser()
    .Build());
```

## Analyzer And Code Fix

No HFC diagnostic or code fix is assigned to this upgrade. The only new signal is the
`InvalidOperationException` that `MapFrontComposerMcp` throws at startup when authentication or
authorization services are missing; its message names the call to add. Requests that 4.7 admitted
through an appended policy now get the authenticating scheme's challenge instead.
