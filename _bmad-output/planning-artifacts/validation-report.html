frontcomposer — UX Design Validation Report

ux-design.md + ux-design-detailed-2026-07-05.md + ux-experience-2026-07-05.md

The three-file UX contract has a clear authority chain and strong FrontComposer/Fluent UI V5 posture, but it is thin to broken as a source-extractable downstream contract. Journey coverage, component identity, lifecycle/state behavior, accessibility mechanics, and source resolution still require inference.

The accessibility and Fluent-specific reviews reinforce that conclusion: the intent is strong, but several behaviors are not deterministic enough to implement or test independently, and two Fluent component names do not exist in the pinned package. Across all lenses: 0 critical, 8 high, 11 medium, and 1 low finding.

1. Flow coverage

broken

The PRD defines six named journeys; the experience supplement has two differently named operator flows.

high

Six source journeys are not traceably covered

prd.md:77-91; experience:138-167
Shell bootstrap, MCP-agent use, compatibility maintenance, and generated-experience testing are absent; overlapping journeys do not preserve source names or protagonists.
Fix: Add verbatim-named flows for every applicable journey or narrow and explain the source/applicability boundary.

2. Token completeness

adequate

All design-token references resolve. Semantic Fluent color roles are valid under the explicit UI-system inheritance.

medium

Load-bearing contrast combinations are not committed

design-detail:19-30,84-94
The document does not name the foreground/background, accent, status, theme, and forced-colors combinations that must retain AA.
Fix: Add an inherited-role/contrast table without duplicating Fluent theme values.

3. Component coverage

broken

The canonical requirements and the two supplement registries cannot be joined deterministically.

high

Component registries are incomplete and name-divergent

canonical:52-62; design-detail:51-71; experience:62-78
Canonical FrontComposer components lack paired visual/behavioral rows; semantically equivalent components use different identifiers.
Fix: Establish one exact-name component registry in both supplements; inherited/no-delta rows are acceptable.

4. State coverage

thin

Core empty, loading, access, stale, reconnecting, and basic command outcomes exist, but surface and lifecycle coverage is incomplete.

high

Lifecycle and blocked-submit states are incomplete

canonical:56-67; experience:75-95
Submitting, Syncing, IdempotentConfirmed, NeedsReview, Warning, Degraded, and the blocked second submit lack state treatments.
Fix: Define evidence, copy, actions, announcements, recovery, timeout, and terminality for every state.
medium

Several IA surfaces lack implementable states

experience:32-47,80-118
Tabs, detail/edit, add/create, offline, validation, network failure, and focus are incomplete.

Accessibility review — thin

review-accessibility.md

WCAG 2.2 AA and core accessibility concerns are explicit, but several interaction-critical behaviors remain too vague for independent implementation and testing.

high

Lifecycle announcements are not deterministic

canonical:64-72; experience:91-116
Transitions, politeness, deduplication, coalescing, and fresh-row expiration are unspecified.
Fix: Add an announcement matrix.
high

Forms lack an accessible validation/rejection contract

experience:73-76,93-94,155-167
Error associations, summary, focus placement, navigation, and client/server distinction are missing.
Fix: Define Fluent-input error semantics, summary links, focus, preserved input, and announcements.
high

Navigation and tabs lack complete focus semantics

experience:45,70,98-105,113
Route heading, selected tab, tabpanel naming, dialog/palette return focus, and failures are not deterministic.
Fix: Define focus and announcement outcomes for each primitive.
medium

Icon-only navigation lacks component-level semantics

design-detail:56-59,134-136
Accessible name, current-page state, tooltip, and badge announcements rely on a global rule.
Fix: Put them in the navigation component row.
medium

Keyboard shortcuts lack conflict and discoverability rules

experience:98-103
Editable-field, IME, localized layout, discoverability, and fallback behavior are absent.
Fix: Define shortcut scope and exceptions.
medium

Responsive accessibility is not measurable

experience:120-128
Reflow/zoom, text spacing, targets, and focus-not-obscured outcomes are missing.
Fix: Add measurable outcomes or cite an inherited conformance contract.
medium

Reduced-motion and forced-colors behavior is not component-specific

design-detail:88-94; experience:115-117
Fallbacks for accent, status, lifecycle, reconnect, and fresh rows are not defined.
Fix: Add component-level fallback rules.

FrontComposer / Fluent UI Blazor V5 review — adequate

review-fluent-ui-v5.md

The inheritance and reuse posture is sound. One API correction and three precision improvements are needed.

high

Two named Fluent components are unavailable

design-detail:63-64,137
FluentToolbar and FluentSearch do not exist in the pinned 5.0.0-rc.5-26219.1 API; current code uses FluentStack role="toolbar" and FluentTextInput TextInputType.Search.
Fix: Correct the names or make FcPageToolbar internals implementation-owned.
medium

Navigation mapping is too vague

canonical:45-47; design-detail:56-59
“FluentButton / FluentNav defaults” does not identify the actual FrontComposer contract.
Fix: Name FrontComposerNavigation and only required Fluent primitives.
medium

Accent alias ownership is ambiguous

design-detail:27,55,82,91
--fc-color-accent could be read as inherited or as a custom theme primitive.
Fix: Bind it to the active Fluent V5 accent role and prohibit an independent palette.
medium

The visual table cannot enforce reuse-first behavior

canonical:52-62; design-detail:51-71
Reusable FrontComposer components are absent from the visual registry.
Fix: Add every component, including explicit inherited-default rows.
