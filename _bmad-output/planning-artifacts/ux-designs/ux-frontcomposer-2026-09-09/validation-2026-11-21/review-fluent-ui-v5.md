# Fluent UI V5 implementation alignment

Reviewed the D-8 UX authority, both designated supplements, the BMad working pair, and the two handoff mockups on 2026-11-21. FrontComposer `431aa71b` records Builds `e1380b813b230022db0b8656ac3a0480e57c07e8`. The catalog at that Git object selects `5.1.0` for both Fluent Components and Icons. The source and package checks below use that selection. This review did not run a hosted Quality lane, an authenticated deployment, or manual assistive technology. [Committed catalog](https://github.com/Hexalith/Hexalith.Builds/blob/e1380b813b230022db0b8656ac3a0480e57c07e8/Props/Directory.Packages.props#L434) · [D-8 UX authority](../../../ux-design.md) · [Product gates](../../../prd.md)

## High

**FL-1. Narrow navigation exposes no Module destination from the hamburger.** The experience contract and responsive mock show a labelled Module list on Tablet and Phone. In the default shell the only fragment containing `FrontComposerNavigation` is inside `HasNavigation && !IsSubCompactDesktopViewport`. That removes the navigation area on both tiers. The header's `FluentLayoutHamburger` receives a title and dialog label but has no child fragment. Inspection of the selected net11.0 package confirms that `get_NavigationContent` returns explicit child content or the registered navigation area's child content. It returns null without either. Disposing a Fluent layout item removes it from the registered areas. [Responsive specification](../EXPERIENCE.md#responsive--platform) · [Shell composition](../../../../../src/Hexalith.FrontComposer.Shell/Components/Layout/FrontComposerShell.razor) · [Viewport guard](../../../../../src/Hexalith.FrontComposer.Shell/Components/Layout/FrontComposerShell.razor.cs) · [Hamburger](../../../../../src/Hexalith.FrontComposer.Shell/Components/Layout/FcHamburgerToggle.razor)

The browser specifications exercise rail activation on desktop and assert a named dialog on phone, successful Escape/focus return, and a visible toggle at tier boundaries. Those assertions would pass with an empty drawer. A follow-up Chromium check used a clean Counter.Web Release build from FrontComposer `431aa71b` with the recorded Builds catalog, .NET SDK 11.0.100 and the repository’s Test/specimens configuration. On a cold load of `/home` at 320 CSS px, pressing Enter on the hamburger opened “Primary navigation” with only its title and Close button. After a 1440-to-320 resize on the Counter route, the drawer had the same contents. At 900 CSS px neither Enter nor a click opened the underlying dialog or exposed a Module list. Both cold-loaded Home pages listed Counter, and at 1440 CSS px the rail successfully navigated to `/counter/counter-projection`. These results describe the local sample.

Supply the authorized Module list to the active narrow navigation surface, and verify keyboard activation on cold phone and tablet loads and across a resize. Assert the Counter destination, default tab, route heading and single current entry. ## Medium

**FL-2. Annotated projection status cells lose their visible label at rest.** UX-DR2 requires a persistent accessible name and visible text accompanying the status icon. The generated annotated enum branch emits a single `FcStatusIcon`. Its focusable `role="img"` has the correct accessible name and Fluent icon, but its text label is inside `FluentTooltip`. A sighted operator must hover or focus the cell to read it. The component tests cover slot-to-glyph mapping, the contextual accessible name, and the tooltip. They do not check for persistent visible text. The older PRD addendum describes the tooltip treatment, while FR-11 and D-8 require the icon-plus-text result. Preserve the current name and semantic glyph, add the persistent label to the generated presentation, and check it before hover/focus and under forced colors. Keep numeric count badges distinct. [UX-DR2](../../../ux-design.md#ux-dr2---semantic-status-slots) · [PRD](../../../prd.md#fr-11-render-projection-grids-and-states) · [Generated column](../../../../../src/Hexalith.FrontComposer.SourceTools/Emitters/ColumnEmitter.cs) · [FcStatusIcon](../../../../../src/Hexalith.FrontComposer.Shell/Components/Badges/FcStatusIcon.razor) · [Component tests](../../../../../tests/Hexalith.FrontComposer.Shell.Tests/Components/Badges/FcStatusIconTests.cs)

**FL-3. Settings conflates a saved choice with the effective density.** The working pair says density selection updates the page behind the dialog and that the dialog session stays silent. On Phone and Tablet, `DensityPrecedence.Resolve` always returns Comfortable before considering the choice, deployment default or surface. Settings retains the selected preference, previews it, and explains when the viewport forces a different effective value. The page can therefore stay Comfortable after selecting Compact. Opening Settings and initial hydration are silent. A later effective density change can announce the localized new value once. Add the viewport override and announcement trigger to the Settings and responsive specifications. Preserve the live, no-Apply interaction and SS-43's silent entry rule. ## Low

**FL-4. The lifecycle mock displays the signed-in name directly in the header.** The mock prints “Marc” in the closed shell header. The working design and the shipped account control place the display name inside the menu, with a Fluent avatar as the trigger. The responsive mock already illustrates that anatomy. Use the same closed avatar in the lifecycle mock. The lifecycle messages and budgets are independent of this change. - The tier watcher uses 768, 1024 and 1366 CSS px. The framework rail uses 72 px on expanded Desktop, 48 px on collapsed Desktop and 48 px on CompactDesktop. CompactDesktop also uses the responsive hamburger control. The default header renders its hamburger before optional header-start content and its account menu after header-end content.
