# Reviewer Gate — Security / Supply-Chain Trust Boundary Lens (VALIDATE)

- **Object:** `ARCHITECTURE-SPINE.md` (GOV-1 dependency provenance, status `final`, updated 2026-07-19)
- **Lens:** ad-hoc security / supply-chain trust boundary
- **Date:** 2026-09-08
- **Grounding read (not under review):** `.github/workflows/ci.yml`, `release.yml`, `release-evidence.yml`; `eng/dependency_graph.py`, `eng/dependency_handoff.py`, `eng/dependency-graph-policy.json`; repository has no `CODEOWNERS`.
- **Threat model applied:** an untrusted PR candidate must not expand trust, inject commands, substitute the released revision, or get a wrong publication authorized; mutable refs in the evaluator chain are non-conforming.

## Verdict

**PASS WITH FINDINGS** — no open path to attacker-controlled publication was found (0 Critical). One High: delayed activation (AD-12) covers the declarative policy and workflow blobs but not the executable evaluator (`eng/*.py`, Governance tests), which runs from the candidate revision, so trust can be expanded in a single merged change. Six Medium hardening/silent-dimension gaps and four Low hygiene items.

Counts: Critical 0 · High 1 · Medium 6 · Low 4.

## Detail per finding

### S-1 (High) — Evaluator code is not delayed-activated

AD-12 correctly forbids candidate `.gitmodules`, workflows, and action metadata from defining trust and makes the *policy file* active only from the base revision. AD-13 extends delayed activation to workflow *definitions* via the caller/reusable/action blob closure. But the programs that read the policy and enforce every AD are run from the candidate tree: `ci.yml` checks out `ref: ${{ github.sha }}` and executes `python3 eng/dependency_graph.py …` and `eng/dependency_handoff.py …`; `release.yml` checks out the dispatched SHA and runs `eng/release_prepublish.py`, `eng/release_contract.py`, `eng/dependency_handoff.py`. The spine even binds `eng/dependency_graph.py` into `RELEASE_DEFINITION_FILES` (fingerprinted) but not into the *activation* rule.

Attack: a write collaborator (or an approved PR that a reviewer skims) changes a gitlink to an unapproved commit and, in the same change, edits `load_policy_at_commit`/`require_evaluator_authorized` to accept it. Push CI on `main` runs the modified evaluator with the old policy and emits a well-formed handoff. Release re-runs the same candidate code. Nothing in the spine's delayed-activation story catches it; only human review of the diff does.

Fix options for the story implementer: (a) execute evaluator code from the active policy commit (`git archive <policy_commit> eng/` into `$RUNNER_TEMP`), recording each script's blob SHA-256 next to the policy hash; (b) if (a) is judged too heavy, write the acceptance down so implementers do not assume the protection exists. S-5 is the compensating control if (b).

### S-2 (Medium) — Publication actor and trigger

The implemented `release.yml` is `workflow_dispatch` with API authentication of a successful push-CI run; the spine still describes a `workflow_run` caller passing "the triggering CI run ID and event head". The implemented model is arguably *stronger* (operator intent + API-verified coordinate), but it introduces an authorization question the spine never answers: which principals may dispatch, and is the `production` environment protected by required reviewers? Bind it, and reconcile the trigger wording so implementers do not re-introduce a `workflow_run` hop that automatically publishes on every green CI.

### S-3 (Medium) — Token and secret scoping

`release.yml`'s `release` job legitimately holds `contents: write`, `id-token: write`, `attestations: write`, `issues: write`, `pull-requests: write` and `NUGET_API_KEY`, all delegated to a Builds-owned reusable workflow. The spine's "read-only GitHub token" statement is therefore only true for the authentication stages. The spine should say precisely which stage may hold which permission and forbid `actions: write` anywhere (artifact deletion breaks S-7's immutability assumption), forbid `pull_request_target`, and require that affected-module builds — which execute candidate MSBuild — run secretless with a read-only token. Governance can assert this from the exact workflow blobs already in the AD-13 closure.

### S-4 (Medium) — Bootstrap / TOFU

The bootstrap gate is well-designed on paper (unchanged graph, closed schema, independently approved digest, admin-controlled repository variable, publication frozen). It is not implemented, and the policy now exists on `main`, so the clause is a latent instruction to build a TOFU path nobody needs. Repository variables cannot be set by PR authors (admin/write-settings only) and `vars` are visible but inert in PR runs, so the design was not exploitable by a PR; the risk is purely re-opening it later. Rewrite the clause as historical and make base-policy absence permanently fail-closed. Also name who controls the `RELEASE_ATTESTATION_*` fallback variables the release job already consumes.

### S-5 (Medium) — Review strength for trust-changing files

Delayed activation moves the trust decision to "the merge that lands the policy". That merge is only as strong as branch protection and reviewer assignment, which the spine leaves silent and the repository does not codify (no `CODEOWNERS`). Bind the protection invariants and record their state in evidence so a weakening is visible.

### S-6 (Medium) — Ledger definition and observability

The word "ledger" carries acceptance semantics in AD-14/AD-15 without a definition. Implementation reality: run artifacts (30/90-day retention) plus assets on an immutable GitHub Release. State which is authoritative, who may write it, and that failure dispositions raise an incident rather than only failing a run.

### S-7 (Medium) — Artifact immutability reliance

Fail-closed today because `upload-artifact` v4+ refuses duplicate names and the trusted step's failure fails the run. Make the reliance explicit so a future actions/version change or an `actions: write` grant is recognised as a trust change.

### S-8 (Low) — Idempotency, partial publication, revocation

Deferred entry proposed; implementation already emits `partial-publish-incident.v2` records, which the spine should acknowledge.

### S-9 (Low) — Transport and hashing assumptions

Content-addressing is the real integrity control; say so, and state the SHA-1 acceptance.

### S-10 (Low) — JS action closure semantics

Clarification only; current text is correct in effect.

### S-11 (Low) — Evidence hygiene

No sensitive material found; add a convention row.

## Confirmed sound — trust invariants the spine gets right

1. **Closed-world identity (AD-3, AD-10):** candidate `.gitmodules` URLs are validated but never used as fetch endpoints; remotes are reconstructed from the policy's canonical identity (`_canonical_clone_url`). A PR cannot expand the remote set.
2. **Exact-object provenance (AD-2, AD-4, AD-5):** graph read from immutable objects; strict 40-hex/64-hex; closed JSON schema with duplicate-member rejection; deterministic canonicalization pinned by golden fixtures.
3. **No candidate-controlled execution (AD-8, Conventions):** argv arrays come only from the active policy; `merge_base == event_base` fail-closed; PR candidate is the CI-built merge SHA; nested submodules never initialized; contract-tree materialization rejects symlinks/gitlinks/special modes and enforces byte/file ceilings before extraction.
4. **Delayed activation of declarative policy and workflow definitions (AD-12, AD-13):** policy from `event_base`/`before`; caller blob hash, reusable commit+blob, and every action commit+blob must match an active-policy authorization; a pre-authorized next closure switches only under the policy that pre-authorized it. Runtime `github.workflow_sha`/`job.workflow_sha` are checked against the sealed *and* allowlisted commit, so a compromised Builds repository cannot satisfy the check without a FrontComposer policy change — the loop closes.
5. **Static closure over the release path (AD-13):** Docker actions, mutable refs, `uses:` expressions, YAML anchors, cycles, and limits fail closed; conditions do not prune sources; fetch only exact commits into bounded isolated stores; workflow text never supplies a URL.
6. **Exact-candidate propagation (AD-13, AD-15):** the authenticated handoff candidate is the sole release-candidate authority; no tag, default branch, later `head_sha`, or `GITHUB_SHA` may replace it; `revalidate current main` before protected credentials; live re-collection of the graph at release (`verify-ci --live`).
7. **Fail-closed evidence (AD-9, AD-15):** `publish_authorized=false` before side effects; post-publication verification never authorizes after the fact and cannot green-no-op (`if: always()` artifact, deferred-emission fails when publication occurred); legacy manifests are audit-only, never resealed (AD-14).
8. **Zero-base handling (AD-12):** a zero/unavailable `before` cannot select trust; diagnostics only; `release_eligible=false`; gate fails (confirmed in `dependency_graph.py` and `ci.yml`).
9. **Resource ceilings (AD-7):** measured before decode; `cat-file -s` before blob reads; boundary fixtures.
10. **`workflow_run` second hop (AD-15):** runs the default-branch definition, read-only token, derives live root only from the handoff candidate and sealed manifest, and independently re-authenticates the CI artifact.
