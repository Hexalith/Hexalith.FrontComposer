## Detail on the High findings

### AU2-1 — `quality.yml` became an authority without becoming a trust input (AD-13/AD-12/AD-16/AD-18)

The AU-2 fix chose the "second authenticated run" topology. Under AD-13 the release now cannot proceed without
a successful `quality.yml` push run for the dispatched SHA, and the sentence "Every Governance assertion this
spine names as a pin executes inside one of those two runs" makes Gate 2b the place where AD-12/AD-17/AD-18
pins are proven. But every other AD still treats `quality.yml` as if it did not exist:

- AD-12's registry is keyed by exactly `ci`, `release`, `post_release`; a `quality` row is schema-invalid.
- AD-12 Bindings list the policy, `ci.yml`, `release.yml`, and five `eng/*.py` files as members of both
  definition lists; `quality.yml` is in neither (`release_evidence.py:123-165`), so a fallback approval survives
  a `quality.yml` edit, and the AD-17 `definition_digest` does not change when Gate 2b is deleted.
- AD-18 Binds name `ci.yml`, `release.yml`, `release-evidence.yml`, and the reusable; `quality.yml` holds
  `secrets.GITHUB_TOKEN` in two jobs (`:216, 732`) and is not asserted.
- `quality.yml` runs `Hexalith/Hexalith.Builds/Github/initialize-build@main` and `initialize-dotnet@main`
  (`:49, 51, 600, 686, 688`). AD-13 forbids `@main` "anywhere in the closure" — and `quality.yml` is in no
  closure, so the mutable reference is conforming.

Unit A (shipped) is therefore fully conforming while a Builds `main` change alters the environment the
Governance lane runs in, and a `quality.yml` change that removes Gate 2b leaves every sealed digest and every
fallback approval intact. Unit B treats `quality.yml` as a fourth caller. The tightening (table) is mechanical
but touches the definition lists and forces `quality.yml` onto a literal Builds pin, so it needs the Architect
and Release Owner. The shipped `select_exact_ci_run` (`release_contract.py:262-263`) also still authenticates
only `ci.yml`, which is an implementation nonconformance against the new AD-13 text.

### AU2-3 — The ancestor clause fails closed on every conforming caller (AD-13 static closure)

The AU-1/A-3 tightening added: "every other step whose normalized `path:`/`with.path` equals, prefixes, or is
an ancestor of that directory (a second checkout, another repository, a mutable ref, an expression, or a `run:`
step writing into it) fails closed". Every `actions/checkout` without `path:` checks out into the workspace
root, and the root is an ancestor of `.hexalith/builds-execution`. `release.yml` contains five such checkouts
(`:36, 181, 225, 348, 420`) and `release-evidence.yml` two (`:31, 298`). A collector that applies the sentence as
written finds an "ancestor" step in every caller and can never draft a `release` or `post_release` row — the
same failure class the pass-1 AU-1 carve-out was written to remove. The shipped regex
(`workflow_source_closure.py:42-48`) goes the other way: it considers only a literal
`path: .hexalith/builds-execution`, so a genuine `path: .hexalith` injection is invisible. "Prefixes" as
written is a string prefix, and "a `run:` step writing into it" is not decidable from a blob. The table gives a
path-segment formulation that excludes the workspace root and drops the `run:` clause (the caller blob hash
already binds run-step bytes).

### AU2-5 — "The reusable publication job" is neither observable by the emitter nor unique (AD-15)

The AU-3 fix defines `published` and `publication_started` on "the reusable publication job". From the caller,
the reusable call is one `needs.release.result` aggregating every inner job, with vocabulary
`{success, failure, cancelled, skipped}` and never `null`. From the API, the reusable exposes at least two
write-scoped inner jobs, `release / release` and `release / governed-release`
(`release_disposition.py:18-27`; `CiGovernanceTests.cs:2220` pins the publish gate on "both release and
governed-release paths"). The shipped emitter uses the aggregate (`release.yml:466-468`); the shipped verifier
keys on `release / release` only (`release_disposition.py:86-88`). If the governed path executes under
`release / governed-release` while `release / release` is skipped, the emitter records `published=true` and the
verifier classifies the run as non-governed, after which `release-evidence.yml:209-218` writes
`{published:false, status:"recorded"}` — a green no-op on a run that pushed packages. Both units obey the
sentence; the tightening pins the aggregate for the emitter, "any `release / *` inner job not skipped" for the
verifier, and a fail-closed comparison between the two. Whether the governed path really runs under
`governed-release` must be confirmed against the pinned reusable at `reusable.commit`, which this pass could not
read (`references/` excluded).
