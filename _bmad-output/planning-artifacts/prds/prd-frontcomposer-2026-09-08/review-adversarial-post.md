# Adversarial Review (Post-Reconciliation) — Hexalith.FrontComposer PRD

Reviewed: `_bmad-output/planning-artifacts/prd.md` (frontmatter `status: draft`, `product_approval: pending-reapproval`, `v1_publication_authorized: false`, `updated: 2026-09-08`) with `_bmad-output/planning-artifacts/prd-addendum-2026-09-08.md`. ## Verdict

**Send back.** The rewrite fixed the shape of the old complaints — split statuses, a blocker table, an FR-19 token table, a package inventory, three-way §5.0 — and in doing so exposed that the gates do not gate anything. `v1_publication_authorized: false` sits above a repo that published **three releases** (v4.2.0 2026-08-30, v4.3.0 2026-09-05, v4.4.0 2026-09-07) while the ledger it cites still says "Further production publication remains unauthorized until that sign-off." The PRD's answer is OI-8: backfill rows. That is the same laundering the last review killed, now pointed at the ledger instead of the frontmatter. On the security side, FR-19 now promises "hidden and absent are indistinguishable" in the same table that admits `resources/list` is a static, ungated catalog, and the code path for an absent resource URI never reaches the FrontComposer token at all. The security reviewer is also named owner of the residual (OI-2) the PRD has already filed under "Accepted residuals." I am being asked to sign my own pre-signed acceptance.

Two of six §0.1 gates (G-2, G-3) are not verifiable against the repo as written; two more (G-4, G-5) are signatures with "Default: accepted" open items behind them. The MCP leak/oracle audit (SM-4) and the allow-all enforcement (OI-3) are excluded from the ship set by construction. A builder *can* read the minimum ship set from §0.1 + §5.0 — and the honest reading is "paperwork plus one Tenants demo"; the security audit is not on it.

## Findings

Spot-check: `git for-each-ref` shows `v4.2.0 2026-08-30`, `v4.3.0 2026-09-05`, `v4.4.0 2026-09-07`. The PRD's treatment: FR-24 "REL-AI-1 … is not a pre-condition of that release — the circular reading in the 2026-08-12 text is withdrawn"; OI-8 "Record ledger rows for v4.2.0, v4.3.0, v4.4.0"; A4 "tags … correspond to published NuGet packages. Disposition: inferred." The addendum §6 keeps REL-AI-1 because "Owner sign-off of published bytes is the only human control left in the chain" — a control that provably stops nothing. FR-24's own consequence "Every published tag has a ledger row" is already violated three times and is filed as a Table A "gated by G-1" item, not as a breach. *Fix:* Before G-1 can be pass/fail, record a dated disposition for each of v4.2.0–v4.4.0: who dispatched, which manifest/classification, whether `publish_authorized=true`, whether GOV-1's "before the next accepted governed release manifest" condition was waived or breached, and whether each is compliant or non-compliant. Do not keep `v1_publication_authorized: false` over a repo that publishes weekly.

- **critical** The MCP resource surface breaks FR-19's own guarantee; the residual is pre-accepted by the reviewer being asked to sign (§5.5 FR-18, FR-19 rows 4 and 7, §9 SM-4, §12 D-14, §12.1, §12.2 OI-2, addendum §5) — Note: FR-19 preamble: "collapse every admission failure to the opaque public shape below so that hidden and absent are indistinguishable." Row 7 of the same table: "`resources/list` | Returns the static generated descriptor catalog; it is not tenant-scoped data (accepted residual, OI-2)." If the full URI catalog is public, `unknown_resource` on read tells the caller "exists but hidden" for every URI in the list and "absent" for every URI not in it. Spot-check of the code makes it worse: (1) `FrontComposerMcpServerOptionsConfigurator` adds every projection and skill resource to `McpServerOptions.ResourceCollection`, exposing `Uri`, `Name`, `Title`, `Description`; no `WithListResourcesHandler`/`WithReadResourceHandler` override exists anywhere in `src/Hexalith.FrontComposer.Mcp`. (2) `MapFrontComposerMcp` returns `endpoints.MapMcp(route)` with no `RequireAuthorization()`; nothing in FR-19 obliges the host to authenticate the endpoint, so the default is unauthenticated enumeration of every bounded context and projection name in the deployment. (3) `FrontComposerMcpResource.IsMatch` is exact-string; a URI matching no registered resource never reaches `FrontComposerMcpProjectionReader.ReadAsync`, so the `unknown_resource` token is produced only for *registered* resources. Absent URIs fall to the ModelContextProtocol SDK's default not-found path — a protocol error, not the FR-19 text token. Row 4 ("`resources/read` for an unknown … projection | Text token `unknown_resource`") is therefore unverified for the "unknown" case it names. Every `unknown_resource` test I found (`ProjectionReaderTaxonomyTests`, `ProjectionReaderSchemaGateTests`, `ProjectionReaderCoverageTests`, `SkillResourceTests`) calls the reader directly, never the SDK dispatch over `ResourceCollection`. Then governance: OI-2 owner is "Security reviewer"; D-14 already says "`resources/list` exposing the static descriptor catalog is an accepted residual (OI-2)"; §12.1 lists it under "Accepted residuals"; the addendum §6 rejects gating it "pending security confirmation." The document accepts the residual, then asks security to confirm the acceptance. *Fix:* Either (a) route `resources/list` and `resources/read` through the visibility gate (own the handlers; hidden and absent both yield the same `unknown_resource` `ReadResourceResult`, and `resources/list` is filtered per tenant or returns empty on auth/tenant failure exactly like `tools/list`), or (b) rewrite FR-19's preamble to say "indistinguishable for tools; resources disclose the static catalog" and require `RequireAuthorization()` (or equivalent) on `MapFrontComposerMcp` as an FR consequence. Add a wire-level test for an unregistered URI through the SDK. Move OI-2 out of "Accepted residuals" until a named security reviewer other than the PRD author signs it with a date.

### Medium

- **medium** `tools/list` cardinality is an auth-state oracle (§5.5 FR-19 row 1, §9 SM-4) — Note: FR-19 row 1: "`tools/list` with no auth, missing tenant, or catalog failure | Successful `ListToolsResult` with an empty `Tools` collection." Spot-check `FrontComposerMcpServiceCollectionExtensions.ListToolsAsync`: on success it returns `[.. catalog.Tools, ToLifecycleTool(options)]` — the lifecycle tool is appended unconditionally, so any authenticated caller receives at least one tool and only a failed caller receives zero. "Empty list" is therefore a precise signal that credentials/tenant were rejected, which contradicts the code comment "do not surface AuthFailed/TenantMissing as a distinct error." It also exposes the lifecycle tool name to every authenticated tenant even when that tenant has no visible commands. Credential-validity oracles are often tolerated; they are not what FR-19's preamble promises. *Fix:* Either list the lifecycle tool only when `catalog.Tools` is non-empty (so zero-visible and failed collapse to the same shape), or amend FR-19 row 1 to state that the empty list is distinguishable from an authenticated empty catalog and that this is accepted, with an owner.

- **medium** No timing statement anywhere in the security contract (§5.5 FR-19, §9 SM-4, addendum §5) — Note: The prior review asked SM-4 to include "timing." The new SM-4 lists shapes, oracles, echoes, and allow-all; timing is absent. Code reading: `ResolveAsync` builds the visible catalog (per-descriptor gate + policy evaluation) for every call, then exact-matches; hidden and unknown both fall to `FindSuggestion`, so the coarse path is shared. Visible tools additionally run `SchemaNegotiationRuntimeGate.EvaluateCommand`. Nobody has measured any of this; the only `Stopwatch` uses in `Mcp.Tests` are performance guards, not oracle checks. Absence of a claim is not a leak, but a signed security contract should say either "timing is out of scope for v1.0" or "timing is bounded by test X." *Fix:* Add one sentence to FR-19 declaring timing in or out of scope; if in, add it to the SM-4 suite.

- **medium** Half the SM "State" annotations are pointers, not evidence (§9) — Note: Verifiable: SM-1 "unmet" (true), SM-2 (matches ledger), SM-7 (`tests/9-8-live-acceptance.md`, verified). Not verifiable from the PRD: SM-5 "met by Story 11.6," SM-8 "met by Story 11.2 evidence," SM-9 "H1–H12 closed" — no artifact path, no test name, no lane. SM-3 and SM-6 carry no State at all. §9's own rule is "Each metric names its evidence." *Fix:* Every SM gets a path or test class; SM-3 and SM-6 get a State or are demoted.

The decision itself ("breaking Fluent update is a FrontComposer major") is fine; the "Default: accepted" and "Blocks: None once confirmed" are the convenient part. *Fix:* Name the catalog profile and revision that carries the pin so it is greppable from this repo; fix `docs/fluent-ui-v5-contingency.md`; state which Fluent GA date, if any, would change the decision.

## What would make this signable

1. **Dispositions for v4.2.0–v4.4.0** — who authorized, which manifest, which classification, whether GOV-1's due condition was waived — recorded in the ledger *before* G-1 is treated as a pass/fail gate. Then either wire §0.1 into `classify-release` or stop calling it a publication blocker list.
2. **A resource-surface decision that matches the code**: gate `resources/list`/`resources/read` through the visibility gate with a wire-level absent-URI test, or rewrite FR-19's guarantee to exclude resources and mandate endpoint authentication. OI-2 signed by a security reviewer who is not the document's author, with a date.
3. **G-2 and G-3 rewritten against the repository**: one authoritative Builds SHA per purpose; the AD-13/AD-15 proof named by run ID or declared unproven; D-12 approver named or the approval admitted as FrontComposer-owned.
4. **A §0.1 row for the SM-4 audit and OI-3 enforcement**, or a signed Product decision to ship without them.
5. **No "Default: accepted" anywhere**; approval gates separated from evidence gates; every SM State pointing at a path.

Until then this PRD describes a release process that is more disciplined than the one the repo is actually running, and signs the description.
