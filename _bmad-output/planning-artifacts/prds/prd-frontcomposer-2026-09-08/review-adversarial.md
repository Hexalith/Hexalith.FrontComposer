# Adversarial Review — Hexalith.FrontComposer PRD

Canonical reviewed: `_bmad-output/planning-artifacts/prd.md` (frontmatter `status: approved-for-v1-readiness`, `updated: 2026-08-12`). Review date: 2026-09-08. Critique only; PRD not edited. Stance: Release Owner + security reviewer asked to sign this as the v1.0 package-release build contract.

## Verdict

**Kill / send back.** This document is not a v1.0 build contract. It is an approved *planning* artifact that still contains unauthorized publication, overdue sequential analyzer gates, an incomplete operator freshness feature, and MCP “fail-closed” language that is weaker than the cited security contract and silent on tenant-gate bypasses. A skeptical Release Owner cannot tell which items actually block ship, and a security reviewer cannot treat §5.5 / SM-4 as an isolation guarantee. Promote it back to draft until there is one named blocker list, one consumer-visible public-surface inventory, and fail-closed MCP rules that match the opaque-token contract — including what is allowed to leak.

## Findings

- **critical** Status launders an unfinished release as v1.0-ready (§ frontmatter, §0, §12 D-9 / D-6 / D-10 / D-11) — Note: YAML `status: approved-for-v1-readiness` plus D-9 “Product approved D-1 through D-8 and the accepted assumption dispositions; PRD status promoted to `approved-for-v1-readiness`” with **Blocks: None**. That is document-approval theater. The same register still says D-6 “Blocks the next NuGet or GitHub package publication and REL-AI-1 closure”, D-10 “Story 11.23 and v1.0 publication authorization”, D-11 “GOV-1 implementation and the next accepted governed release manifest”, and FR-24 “publication remains unauthorized.” The PRD itself names the trap in §10: “Workflow success is confused with release readiness.” D-9 is that trap, signed. *Fix:* Split statuses. Keep PRD-approval separate from product-ship authorization. Change the live status to something that cannot be misread as “approved to publish v1.0.” Put a single **v1.0 publication blocker list** above the FR table: REL-3 live evidence, REL-4 frozen-run proof, REL-5 signing identity, REL-AI-1, GOV-1 / BUILD-REL-1, Stories 9.4–9.8, Stories 11.20–11.23. D-9 Blocks must not read “None” while any of those remain open.

- **critical** Publication gates are circular; REL-AI-1 cannot close without the release it forbids (§5.7 FR-24, §12 D-6) — Note: FR-24 says “`REL-AI-1` can be marked done only after a real release records `classification=ready`, `publish_authorized=true`…” and, in the same requirement, “publication remains unauthorized.” REL-4 “source control exists but is not yet accepted as operational proof.” REL-5 still owns “production signing identity, certificate custody, timestamp-authority approval… first gated-release authorization.” D-6 records Hexalith.Builds issue 17 “closed… without the GOV-1 amendment,” then treats a reopen/successor as the unfreeze gate while “FrontComposer-local GOV-1 work proceeds.” You cannot prove the exact-artifact gate with a release you are forbidden to cut, and you cannot cut v1.0 until the gate is proven. That is not a hard requirement; it is a bootstrap paradox buried in one FR. *Fix:* Define a named, non-customer **gated evidence release** (or unsigned dry-run with production-equivalent classifiers) that is allowed to run once to close REL-AI-1, with an explicit rule that it is not v1.0. Or drop REL-AI-1 as a pre-v1.0 completion criterion and make the first *customer* v1.0 the closure event — pick one, date it, and stop encoding both.

- **critical** MCP “fail-closed / no existence oracle” is not specified tightly enough to sign, and it is weaker than the security contract (§2.4 UJ-4, §5.5 FR-17–FR-19, §6 NFR-5, §9 SM-4) — Note: UJ-4 claims “auth, tenant, unknown resource, and schema mismatch failures do not reveal existence or internals.” FR-19 says hosts “return hidden-equivalent failures for sensitive cases” and “Auth failed, tenant missing, unknown resource, and unknown tool cases do not become existence oracles.” That vocabulary is not a protocol. Spot-check of `_bmad-output/contracts/fc-mcp-fail-closed-security-contract-2026-06-05.md` (load-bearing, suspiciously smooth PRD claim) shows the PRD omitted the parts a security reviewer would actually bind:
  - `tools/list` on auth/tenant failure is a **successful empty list**, not the same envelope as `tools/call`. That *is* an oracle: empty catalog vs “unknown tool.”
  - Skill resources “intentionally bypass `IFrontComposerMcpResourceVisibilityGate`.” FR-18 only says they are “served only from validated `agent-reference` sections.” Tenant isolation for skills is not a PRD rule.
  - Sample/dev **allow-all gates** are an explicit, ordered escape hatch in the contract. The PRD never forbids shipping `AllowAll*` in a production host.
  - Schema contract `_bmad-output/contracts/fc-mcp-schema-fingerprint-negotiation-2026-06-05.md` allows **`CompatibleAdditive` and `CompatibleWarning` to proceed with side effects**. FR-19 only says “Incompatible schema fingerprints block side effects.” Compatible-with-warning is a silent product decision to mutate on a drifted schema.
  - Two fingerprint algorithms are public wire (`frontcomposer.schema.sha256.canonical-json.v1` and `…sourcetools-blob`). §11 never names them.
  SM-4 then validates FR-17–19 by “tests cover…” — coverage of named cases, not “no tenant/schema/existence leak in any public MCP response.” NFR-5’s “MCP and Shell security fail closed” gives the Shell **zero** opaque-failure taxonomy. *Fix:* Promote the opaque public tokens (`unknown-tool` / `unknown_resource` / `Request failed.` / empty `tools/list`) into FR-19 with a table of request class → public shape. Explicitly state skill-resource tenant bypass and the production ban on allow-all gates. Name CompatibleAdditive/Warning as an approved side-effect class or forbid them for v1.0. Put dual fingerprint algorithms in §11. Replace SM-4 with an independent leak/oracle suite (timing, list-vs-call, skill vs projection, schema-hint echo, log redaction) owned by security, not “tests exist.”

- **critical** Stories 11.20–11.23 are a v1.0 publication gate on a schedule that has already failed (§5.0 FR-29, §8.2, §12 D-10, epics due dates) — Note: §8.2: “Stories 11.20–11.23 are sequential, separately approval-gated backlog phases due **2026-07-24 through 2026-09-11**; 11.23 is required before v1.0 publication authorization.” Today is **2026-09-08**. Epic due dates: 11.20 **2026-07-24**, 11.21 **2026-08-14**, 11.22 **2026-09-04**, 11.23 **2026-09-11**. Three of four dates are already past; 11.23 is three days away; all four remain **backlog** behind “in review” parents. Each phase “requires separate Architecture/Product approval.” Treating analyzer burn-down of thousands of findings (epics cite 2,958 Naming + 367 product + 503 generator + 3,500 test + 203 sample) as a remaining v1.0 *publication* gate is how you either slip v1.0 indefinitely or rubber-stamp 11.23. D-10’s “unless a dated replacement decision provides equivalent diagnostic ownership” is an escape hatch, not a plan. *Fix:* Either re-date 11.20–11.23 with a honest critical path and remove 11.23 from the v1.0 *publication* gate (keep it as post-v1.0 quality), or freeze v1.0 until a replacement decision is signed. Do not leave “due 2026-07-24” in a document still marked approved-for-v1-readiness on 2026-09-08.

- **high** FR-24 / FR-26–FR-29 / REL-* / GOV-1 bundling hides what actually blocks v1.0 (§5.0, §5.7) — Note: The status map is a smoothing machine. FR-14–FR-23 are “Baseline / release verification” even though FR-19’s own consequences call MCP lifecycle remediation “**v1.0-blocking**.” FR-24 is a novella: inventory, signing, timestamp, SBOM, v2 manifest, dependency graph, evaluator identity, REL-2/3/4/5, REL-AI-1, BUILD-REL-1, issue 17, freeze guard. FR-27 is “Complete / release verification,” FR-28 “Complete decision records,” FR-29 “Active release-readiness program” that then swallows four workstreams plus 11.20–11.23. A builder cannot answer “what is the minimum ship set?” without a second ledger. Epic 9 row-freshness (FR-13/FR-26) sits next to signed-NuGet provenance as if they were the same kind of gate. *Fix:* Split the map into **v1.0 ship blockers**, **v1.0 regression baselines**, and **closed decision records**. Promote REL-3, REL-4, REL-5, REL-AI-1, GOV-1, 9.4–9.8, and 11.23 to first-class gate IDs with one owner, one evidence artifact, and one pass/fail sentence each. Demote FR-27/FR-28 from the active FR list.

- **high** No consumer-visible public-surface inventory (§4, §5.7 FR-24, §11, §12 D-5) — Note: §11 is a category list: “attributes and Generated Output path,” “HFC diagnostics,” two CLI JSON schema names, “MCP tool/resource schemas and Schema Fingerprints,” “Testing package public API,” “Release package inventory,” “Contracts.UI split.” It does not name package IDs, `PublicAPI*.txt` files, MCP tool names, diagnostic bands, or the generated-output path versioning rule. FR-24 requires publishing “only the expected NuGet package set” without listing it. Spot-check of `eng/release-package-inventory.json` (the implied inventory) names eight packable IDs plus unpackable AppHost and UI. The UI row says it “is run or published as a **container image**,” while §4 says the product “**does not ship FrontComposer-owned containers**.” That contradiction is unsigned. A package consumer cannot know the v1.0 surface; a Release Owner cannot inventory-validate against the PRD. *Fix:* Add a single table: package ID, packable yes/no, public-API baseline file, TFM, breaking-change policy. Name the eight packable packages. Resolve UI/AppHost: container, sample-only, or out of v1.0. Put MCP tool/resource identifiers and HFC diagnostic bands in that inventory or explicitly defer them to a named contract with a hash.

- **high** Operator jobs are the vision; developer/CI activity is the scoreboard (§1, §2, §9) — Note: Vision: “operations-ready Blazor UI” and “browse projections, understand status, and execute commands safely.” UJ-2’s value “lands when Marc can identify the relevant row and **trust whether the read model is current**.” UJ-3’s value lands when the UI “distinguishes accepted command transport from projection-confirmed outcome.” Primary success metrics: SM-1 adopter bootstrap, SM-2/SM-2a release/provenance, SM-3 drift visibility, SM-4 MCP **test coverage**. Secondary: SM-5 harness usefulness, SM-6 “release checks report zero new raw interactive controls.” There is **no** operator outcome: time-to-trust a row, command-confirmation error rate, stale-data incident rate, accessibility task success. SM-C2 says visual polish cannot outrank contract safety — it does not say CI greenness cannot outrank operator trust. Shipping a generator+NuGet story as v1.0 while FC-NIP composition is still in remediation means the named operator value is optional. *Fix:* Either restate v1.0 as a **developer-framework / package-safety** release and move operator freshness (FR-13/FR-26) out of the ship thesis, or add operator SMs that fail the release if Marc cannot trust freshness and command terminal states. Do not keep both theses.

- **high** D-4 “Resolved” while Stories 9.4–9.8 still block the operator freshness feature (§5.0 FR-13, §5.3, §5.7 FR-26, §12 D-4 / §12.1) — Note: D-4: “**Resolved** 2026-08-12” then “D-4 is resolved; Stories 9.4-9.8 still block FR-13/FR-26 completion and Epic 9 closure.” §12.1 repeats that “All PRD open questions… are now resolved” while composition “remains in active remediation.” A 2026-08-11 retrospective “rejected Story 9.2 evidence as proof of composed behavior.” Decision-resolved / product-unshippable is exactly the smoothing this review is for. UJ-2 still sells row trust. *Fix:* Mark D-4 as **decision recorded, composition not accepted**. Add an explicit v1.0 product choice: (a) FC-NIP composition is a ship blocker, or (b) v1.0 ships **without** automatic row marking and UJ-2 is rewritten. Do not leave a resolved diamond on an open release gate.

- **high** Assumptions A1/A2 are treated as approved product law (§2.4, §4, §12 D-9, §13) — Note: A1 started as “[ASSUMPTION A1: the target v1.0 Testing harness must cover…]” and is **Disposition: accepted as a v1.0 requirement**. A2 “v1.0 readiness is judged primarily by package-consumer safety and Hexalith domain-module adoption, not by a public web launch funnel” is accepted as “the v1.0 product-form-factor assumption; validated by SM-1 and SM-2.” D-9 then blesses “accepted assumption dispositions” as the reason the PRD is `approved-for-v1-readiness`. Assumptions that rewrite the ship thesis (what v1.0 *is*) are not residual risks; they are unvalidated strategy. SM-1’s “preferably Tenants” is not a named adopter commitment, so A2’s “domain-module adoption” has no obligated consumer. *Fix:* Promote A1 into FR-22 acceptance with named failure states as a gate, or demote it from v1.0. Replace A2/SM-1 “preferably” with a named module, named bootstrap path, and a dated evidence artifact. Remove “assumption” language from anything D-9 treats as law.

- **medium** Dual “canonical” PRD copies, one path already gone (§0, §12 D-1) — Note: “The readiness-discoverable canonical copy is `_bmad-output/planning-artifacts/prd.md`; the BMad run copy is `_bmad-output/planning-artifacts/prds/prd-frontcomposer-2026-07-05/prd.md`.” D-1: “Resolved” / **Blocks: None**. Spot-check: that 2026-07-05 run copy is not at the cited path; it lives under `planning-artifacts/archive/prds/`. Two-source-of-record plus a dead path is how agents implement the stale one. Frontmatter `updated: 2026-08-12` is also stale relative to this 2026-09-08 readiness pass. *Fix:* One canonical path. Archive or delete the run-copy claim. If a dated snapshot is required, mark it **immutable historical**, not a second PRD.

- **medium** FR-19 is labeled baseline while its own text says v1.0-blocking (§5.0, §5.5 FR-19) — Note: Status map: “FR-14 to FR-23 | Baseline / release verification.” FR-19 consequence: “Epic 11 MCP lifecycle cross-request remediation is **v1.0-blocking** because lifecycle subscribe/poll is part of the agent contract, not an optional diagnostic.” §8.2 says Epic 11 runtime “baseline stories done; 11.18a is in review.” A baseline FR cannot carry an open blocking remediation without a child ID and evidence owner. *Fix:* Split FR-19 into (a) fail-closed admission baseline and (b) cross-request lifecycle gate with a story ID and pass/fail evidence. Stop calling the parent “baseline.”

- **medium** §12.1 claims every open question is resolved while publication, analyzers, and GOV-1 are not (§12.1 vs D-6, D-10, D-11) — Note: “All PRD open questions identified by the 2026-07-05 readiness follow-up are now **resolved, routed, or explicitly accepted**.” Routing an upstream miss (Builds issue 17 closed without GOV-1) is not resolution. “Local work proceeds” while reusable-workflow integration still “gates… release eligibility, and unfreeze” is a buried blocker. *Fix:* Replace the paragraph with three lists: closed, routed-with-named-external-owner-and-date, accepted-residual. Anything that still blocks NuGet/GitHub publication cannot appear only in the “resolved” column.

- **medium** SM-4 / SM-6 / NFR-11 measure activity and CI greenness, not adopter safety (§9, §6 NFR-11) — Note: SM-4 “tests cover missing gate startup failure, hidden-equivalent…” SM-6 “release checks report zero new raw interactive controls…” NFR-11 “the v1.0 release gate includes the default solution-level lane with `DiffEngine_Disabled=true`, Governance, Contract, snapshots…” Those are necessary hygiene. They are the same class of metric the §10 risk warns against: a green workflow that still has `classification=blocked`. Counter-metrics SM-C1–C3 attack generated-file count, visual polish, and CLI verbosity — not “CI green ⇒ ship.” *Fix:* Add a counter-metric: **workflow green with `publish_authorized=false` is not release success.** Bind SM-2 to the classified manifest, not to lane pass. Bind MCP success to a leak/oracle audit, not to test-count.

- **medium** Fluent UI Blazor **RC** is pinned as a v1.0 runtime constraint (§7) — Note: “Fluent UI Blazor v5 pinned centrally at `5.0.0-rc.4-26180.1`.” Shipping signed v1.0 packages on an RC UI stack is a consumer-safety defect unless the PRD explicitly accepts “v1.0 may break when Fluent 5 stable ships” with a migration owner. It does not. *Fix:* Either require a stable Fluent 5 pin before v1.0 publication, or add a dated exception: RC allowed, breaking Fluent updates are a FrontComposer major, with a named compatibility test pack.

- **medium** Shell / operator tenant isolation is not a requirement; only MCP gates are (§2.1, §5.2–5.4, NFR-5) — Note: Jobs include “without leaking tenant, auth, or schema details” for agents. Operator journeys UJ-2/UJ-3 never mention tenant. FR-10 command palette is “authorization-aware.” NFR-5 lumps “return paths, storage keys, tenant/user scope” into one sentence. Multi-tenant isolation is a stated stake; the PRD specifies it for MCP gates and server-injected fields, not for projection grids, home-directory counts, SignalR groups, or settings storage. *Fix:* Add an FR for shell tenant scope: navigation, queries, SignalR, storage keys, and error text. Define the operator-visible failure when tenant context is missing (fail-closed, not empty-looking data).

- **low** Generated-output path declared a public contract with no compatibility window (§3, §11) — Note: “Generated Output — files emitted under `obj/{Config}/{TFM}/generated/HexalithFrontComposer/`; the path is a **public contract**.” Path-as-contract without a deprecation story means any generator folder rename is a breaking v1.0 change, including for tools that are not package consumers. *Fix:* Version the path or state that only the documented inspect/migrate JSON, not the `obj/` folder shape, is the supported contract.

- **low** “Sensitive cases” and “internals” are undefined in the product FR text (§5.5 FR-19, UJ-4) — Note: Even after fixing the critical MCP gap, the PRD still uses “sensitive cases” and “internals” as if they were enumerated. They are not. *Fix:* Delete those words. Point at the token table.

## What would make this signable

1. One **publication blocker list** that D-9 cannot override with “Blocks: None.”
2. One **package + public-API + MCP identifier inventory** a consumer can grep.
3. MCP FR-19 rewritten to the opaque-token contract, including list-vs-call, skills bypass, allow-all ban, and additive-schema side effects.
4. An honest v1.0 thesis: package-safety framework *or* operations shell with FC-NIP, not both with only CI metrics.
5. Analyzer 11.20–11.23 either re-dated off the v1.0 publication path or replaced by a signed exception.

Until then, do not use this PRD as the v1.0 package-release contract.
