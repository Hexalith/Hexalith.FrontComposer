# PRD Quality Review — Hexalith.FrontComposer Product Requirements Document

## Overall verdict
This is a high-substance brownfield capability spec: the product bet is specific, failed evidence is named rather than smoothed, baseline FRs are mostly testable, and counter-metrics exist. It is not yet a v1.0 build contract. The work that still gates publication — FC-NIP composition, projection realtime recovery, architecture-review defects, analyzer activation — is tracked as story status and epic numbers instead of PRD-carried done-ness, and the success metrics validate bootstrap and package seals rather than those remaining bets. Downstream UX, architecture, and story workflows can extract IDs and contract paths, but they cannot source-extract what “done” looks like for the requirements that actually remain open.

## Decision-readiness — adequate
A decision-maker can act on gates that the register already closed. §12 states decisions as decisions: D-3 freezes `/commands/{BoundedContext}/{CommandTypeName}`; D-4 names what was given up (“never inferred from SignalR nudges”) and what replaced it (`ICommandTargetIdentityProvider<TCommand>` or `SameAsSource`); D-6 records that live v3.2.2 evidence “proved G1 insufficient” and that “publication remains unauthorized”; D-8 explicitly trades a standalone UX spec for `ux-design.md` plus story-local notes. That is honest trade-off language, not template balance.

The register then over-closes. §12.1 says “All PRD open questions identified by the 2026-07-05 readiness follow-up are now resolved, routed, or explicitly accepted.” That sentence is dated and narrow, but a scanner of an `approved-for-v1-readiness` PRD will read it as “nothing left to decide.” Meanwhile D-6 still blocks “the next NuGet or GitHub package publication,” REL-4 “live frozen-run evidence remains outstanding,” Stories 9.4–9.8 still block FR-13/FR-26, and D-10 leaves 11.23 as a publication gate. None of that appears as an Open Question or `[NOTE FOR PM]`. D-9 records that Product promoted this status on 2026-07-05 after approving “D-1 through D-8”; D-4’s successor (2026-08-12), D-6’s 2026-08-02 truth-state correction, D-10 (2026-07-16), and D-11 (2026-07-19) sit in the same table without a re-promotion of status. A pusher-back would find the failed-release history; they would not find a current “what is still undecided vs merely unimplemented” list.

### Findings
- **[high]** Open-question closure hides live publication tensions (§12.1, §12 D-6, §5.7 FR-24) — §12.1 claims the 2026-07-05 question set is “now resolved,” while D-6 still states “publication remains unauthorized” and FR-24 says REL-4 “source control exists but is not yet accepted as operational proof.” There are zero `[NOTE FOR PM]` callouts and no remaining Open Questions. *Fix:* Restore a short open-item list for live gates (REL-4 frozen-run proof, Builds issue 17 successor, Epic 9 composed/live evidence, 11.23 activation) with owner and unblock condition; keep resolved decisions in the register.
- **[medium]** Status approval does not cover later load-bearing rows (§12 D-9 vs D-4/D-6/D-10/D-11) — D-9 is “Resolved 2026-07-05: Product approved D-1 through D-8 … PRD status promoted to `approved-for-v1-readiness`.” Frontmatter `updated: 2026-08-12` includes the FC-NIP successor, analyzer staging, and dependency-provenance regime. Those rows name Product as an owner, but the status line was not re-earned. *Fix:* Add a dated D-9 amendment that Product re-approves the post-July register, or change status until that happens.
- **[medium]** HFCM9002 has no decision-register row (§5.7 FR-27, §12) — FR-27 still requires “HFCM9002 migration-emission behavior is decided and documented” while listing FR-27 as “Complete / release verification.” §12 has no ID, owner, default, or evidence pointer. *Fix:* Either cite the closed decision/artifact in D-* or reopen it as a named gate.

## Substance over theater — strong
The Vision cannot be swapped into a generic admin-framework PRD. “FrontComposer makes the domain type the source of truth and uses source generation, schema fingerprints, and strict governance tests to keep UI, lifecycle state, MCP descriptors, and tooling aligned” is a real bet, and the feature groups follow it. The five named user types in §2.1 are one over the rubric’s comfort line, but each drives FRs (adopter → FR-1–9/22, operator → FR-10–16, AI-agent integrator → FR-17–19, maintainer → FR-20–23/25, release owner → FR-24). UJs have named protagonists and edge cases, not role wallpaper.

NFRs are product-specific rather than “must be scalable/secure.” NFR-4 forbids “raw interactive HTML controls and legacy tokens … except documented carve-outs.” NFR-6 names the leak classes. NFR-13 gives fail-closed numeric ceilings. FR-24 is the opposite of furniture: it is too much mechanism, not empty importance. No finding required on this dimension.

## Strategic coherence — adequate
The thesis is two-part and mostly held: (1) describe the operational surface once in annotated types; (2) v1.0 is package-consumer safety, not a feature launch. §8.1 keeps the baseline; §8.2 says post-MVP work is “row-level command feedback, tooling-governance cleanup, and architecture-quality remediation.” Counter-metrics SM-C1–C3 reject generated-file count, visual polish, and CLI volume. That is thesis-aligned measurement.

The Success Metrics then validate the baseline and the seal, not the remaining bet. SM-1 “validates FR-1, FR-2, FR-7, FR-8.” SM-2/SM-2a validate FR-24/FR-25 and NFR-12/13. SM-3 validates drift. SM-4 validates MCP fail-closed. SM-5/SM-6 cover testing and UX governance. Nothing in §9 validates FR-13, FR-26, FR-12 recovery, or FR-29. A release could pass SM-1 (a module boots) and SM-2 (packages seal) while fresh-row composition is still the rejected 2026-08-11 retrospective and a long-lived circuit still “permanently degrade[s] after reconnect failure.” §5.0 and §8.2 also turn the PRD into a sprint dashboard (“Story 9.3 is the approved successor,” “11.17b–d, 11.18a–c, and 11.19a–d are in review”), which competes with the product thesis.

### Findings
- **[high]** Success metrics do not test the remaining v1.0 product bets (§9 vs §1, §5.0, §5.3 FR-12/FR-13, §5.7 FR-26/FR-29) — Vision says post-MVP “focuses on row-level command feedback … and architecture-quality remediation.” No SM names composed FC-NIP behavior, self-healing projection realtime, or architecture-review defect closure. SM-1’s “preferably Tenants” further softens the one adoption proof. *Fix:* Add SMs (or explicit SM mappings) for composed/live FC-NIP, reconnect-and-recover projection freshness, and the H-series runtime/security closures; make the adopter module a named gate or give substitute criteria.
- **[medium]** Feature prioritization is being replaced by story-status narration (§5.0, §8.2, §5.7 FR-24/FR-29) — The status map and FR-24/FR-29 consequences read as a program ledger (REL-2/3/4/5, Stories 11.20–11.23 due dates, “in review”). That is useful operations text, but it is not prioritization derived from the thesis. *Fix:* Keep one status snapshot table; move REL/story choreography out of FR consequence lists so FRs stay product outcomes.

## Done-ness clarity — thin
Many baseline FRs are genuinely testable and should be credited: HFC1003/1006/1009, density counts `0-1` / `2-4` / `5+`, MCP “startup throws if required MCP gates are missing,” command budgets `10_000` / `1_000` / `120_000` / `250` ms, FC-CNC “blocks later local submits rather than queueing.” Brownfield HFC IDs checked against SourceTools are real. That is not the problem.

The remaining publication-blocking FRs are not done-able from this PRD. FR-29’s requirement is “complete the remaining Epic 11 release-readiness remediation children that address runtime blind spots, maintainability, and enforcement.” Consequences are workstream names, parent-vs-child story hygiene, logging-ownership order, analyzer phase order, and “Acceptance criteria … use Given/When/Then form before ready-for-dev.” Those are process rules. The actual product outcomes — circuit-safe EventStore auth, self-healing projection realtime, MCP cross-request lifecycle, open-redirect/storage-key hardening, fault-injectable Testing, Contracts split (already delivered), LoggerMessage, `AnalysisMode=Recommended` — live in `epics.md` and `_bmad-output/project-docs/architecture-quality-review-2026-07-04.md` as H1–H12 / M-series. The PRD never names those defect classes. An engineer reading only this FR cannot write an acceptance test.

FR-12 is the same failure in a smaller box. UJ-2 promises Marc sees “stale, reconnecting” states. FR-12 consequences stop at “Reconnect and fallback polling states are visible” and “Epic 11 realtime resilience remediation is release-readiness work when a long-lived circuit can permanently degrade after reconnect failure.” That last sentence is a problem statement, not a pass condition. Story 11.2 already carries the missing bounds (~42 s default retry ladder, 15 s fallback polling, unbounded jittered retry, restart-on-`Closed`). NFR-8 then says those states must appear “within configured budgets,” and the only numeric budgets in the PRD are command-lifecycle numbers in FR-15. NFR-9 still says “existing benchmark thresholds and cache caps.” NFR-11 still says e2e lanes “required by the changed surface.” FR-13/FR-26 consequences are “Stories 9.4-9.8 must implement …” — work orders, not observable product rules (the testable rules are in the cited contract files, which is a pointer, not a PRD consequence).

### Findings
- **[high]** FR-29 is a program envelope, not a requirement (§5.7 FR-29, §1) — “runtime blind spots” is an adjective. Consequences govern Epic 11 administration. Architecture-review findings H1–H12 / M-series are not listed, so v1.0-blocking runtime/security/maintainability outcomes are not source-extractable here. *Fix:* Replace FR-29 (or add FR-29.x rows) with one testable outcome per remaining defect class: operator-visible behavior, fail-closed rule, and verification artifact; map each to the H/M ID and story.
- **[high]** Projection reliability has no PRD-carried bounds (§5.3 FR-12, §6 NFR-8/NFR-9/NFR-11) — FR-12 does not say what recovery means, how long fallback polling may last, or when a circuit is allowed to stay degraded. NFR-8 defers to “configured budgets” that FR-15 defines only for commands. NFR-9 leaves “existing benchmark thresholds and cache caps” unnamed. NFR-11’s “lanes required by the changed surface” is not a v1.0 mandatory-lane list. *Fix:* Inline the reconnect/retry/fallback numbers (or cite a named contract), name the benchmark IDs/caps, and list the v1.0 mandatory test lanes.
- **[medium]** FR-13/FR-26 done-ness is a story checklist (§5.0, §5.3 FR-13, §5.7 FR-26, §12 D-4) — The product rule (“never infer row-level fresh indicators from projection nudges that lack row identity”) is clear; the completion rule is “Stories 9.4-9.8 must pass.” Terminal path, invalidation, scope, first-wins, and composed/live gaps are named as remaining work but not as observable conditions. *Fix:* Promote those gaps to FR consequences (one producer boundary, scope-safe state, atomic first-wins, composed/live evidence artifact) and let story IDs be references, not the definition of done.
- **[medium]** Catalog FRs defer the testable part to “documented” (§5.1 FR-3, §5.1 FR-1, §5.2 FR-9, §5.3 FR-11) — FR-3 lists a vocabulary then says “Unsupported or invalid attribute use emits the corresponding HFC diagnostic.” FR-1 requires “the documented five-file set” without naming the files. FR-9 caps layout at “the documented max measure.” FR-11 activates column prioritization “when thresholds are met.” UJ-2’s `stale` state is not in FR-11’s consequence list. *Fix:* Name the five files, the measure, the column thresholds, and the projection-state set in the PRD, or cite a single canonical contract per item.

## Scope honesty — adequate
§2.3 Non-Users and §8.3 Out Of Scope do real work: no-code CRUD, non-Blazor surfaces, replacing EventStore, rich `<AuditTimeline>` / `<ConsequencePreview>`, hand-authored Tenants/Parties page bodies, nested submodules. Delivery honesty is unusually good: rejected Epic 9 retrospective, unsigned v3.2.2 packages, G1 insufficient, issue 17 closed without GOV-1, REL-4 not yet operational proof. `[ASSUMPTION]` A1/A2 are indexed and disposed.

Omissions that a reader could silently assume are the problem. There is no `[NON-GOAL for MVP]` on EventStore runtime-identity adoption, even though `epics.md` Story 11.24 sits in Epic 11 as blocked backlog pending EventStore Story 1.20 and “must not move to `ready-for-dev`.” The PRD never mentions 11.24. A chain-top reader will fold it into FR-29 or miss it. Assumption density is two tags on a reverse-engineered, high-stakes PRD (Risk §10 admits “PRD traceability started from reverse-engineered artifacts”); density thresholds, command budgets, Fluent RC pin, `AnalysisMode=Recommended`, and “preferably Tenants” are inferences without `[ASSUMPTION]`. §8.2 still says Stories 11.20–11.23 are “due 2026-07-24 through 2026-09-11”; 11.20’s due date is already past relative to this review (2026-09-08) and the PRD’s own `updated: 2026-08-12`. There is no single v1.0 blocker inventory. There is no `addendum.md` beside this PRD; historical run-folder depth from 2026-07-05 is not replaced, so overflow either bloated FR-24/D-11 or was dropped.

### Findings
- **[high]** Story 11.24 / EventStore runtime identity is invisible here (§8.2, §8.3, §12 vs Epic 11) — Epic 11 now includes a blocked identity-adoption story that the PRD does not list as in-scope, non-goal, or deferred. Readers will either treat it as a silent FR-29 child or ship v1.0 without noticing the gate. *Fix:* Add an explicit in-scope / `[NON-GOAL for MVP]` / deferred row: activation condition, what v1.0 must not change, and whether publication may proceed while it stays backlog.
- **[medium]** Open-item and assumption density is too clean for the stakes (§12.1, §13, §8.2) — Two accepted assumptions and zero open questions on a green-light-to-build PRD whose publication is frozen. §8.2 due dates already slip past 11.20 (2026-07-24) and 11.21 (2026-08-14). *Fix:* Tag remaining inferences; publish one v1.0 blocker table (blocker, FR/D, owner, unblock condition, blocks-stories vs blocks-publication); refresh or remove due dates.
- **[low]** Addendum depth was dropped (document surface) — No `addendum.md` sits next to the canonical PRD. Rejected-alternative rationale and mechanism that used to be extractable overflow now either inflate FR-24/D-6/D-11 or are gone. *Fix:* Re-home REL/GOV mechanism and source inventory to addendum or architecture; keep product outcomes in the PRD.

## Downstream usability — adequate
This is a chain-top PRD; this dimension counts. IDs are contiguous and unique: UJ-1–UJ-6, FR-1–FR-29, NFR-1–NFR-13, SM-1/SM-2/SM-2a/SM-3–SM-6 plus SM-C1–C3, D-1–D-11, A1–A2. Assumptions roundtrip. Every UJ has a named protagonist (Nina, Marc, Ravi, Camille, Sophie) with inline context. Contract paths for FC-NIP and command routes are concrete. D-2 tells UX and architecture where canonical companions live.

Extraction still snags. UJ-2 says Marc “sees bounded contexts ordered by urgency”; FR-10 and the glossary say operators see a **Module** with a required **Module Tab** and `/{module}/{tab}`. Command routes keep `{BoundedContext}` (D-3). Glossary **Command Lifecycle** is “Idle through Submitting, Acknowledged, Syncing, and terminal outcomes”; FR-15 adds Confirmed, Rejected, IdempotentConfirmed, NeedsReview, Warning, and Degraded; UJ-3 lists a third, shorter set and omits Warning/Degraded. Customization “Level-2/3/4,” EventStore, REL-*/GOV-1, and `hexalith.release-evidence.v2` are load-bearing nouns not in §3. D-1 still names `_bmad-output/planning-artifacts/prds/prd-frontcomposer-2026-07-05/prd.md` as “the BMad run copy”; that folder is archived, and this validation run is a different path. FR-24 cannot be pulled out as one story-sized requirement. FR-29 cannot be pulled out as a requirement at all. D-8 already admits “UX requirements remain too compact for visual stories” (§10) — correct as a decision, costly for the UX workflow this PRD claims to feed.

### Findings
- **[medium]** Operator IA nouns are not identical across UJ, glossary, and routes (§2.4 UJ-2, §3, §5.3 FR-10, §12 D-3) — UJ-2 still says “bounded contexts”; FR-10 says “one Module … `/{module}/{tab}`”; command activation is `/commands/{BoundedContext}/{CommandTypeName}`. *Fix:* Use Module/Module Tab in operator UJs; keep Bounded Context as the adopter/generator noun; state that command-route `{BoundedContext}` is the technical segment, not the chrome label.
- **[medium]** Canonical copy vs run copy is stale (§0, §12 D-1) — Canonical path is `_bmad-output/planning-artifacts/prd.md`. D-1 still points at the 2026-07-05 BMad run copy. There is no anti-drift rule, and the registered run path is no longer the live validation workspace. *Fix:* Point D-1 at the current run folder or declare the canonical file the only source of record and mark run copies as generated mirrors with a sync owner.
- **[low]** Command-lifecycle vocabulary does not roundtrip (§3 Command Lifecycle, §5.4 FR-15, §2.4 UJ-3) — Glossary under-lists states that FR-15 requires; UJ-3 omits Warning and Degraded. *Fix:* Make the glossary list the FR-15 state set and align UJ-3, including degraded/timeout as a landing.

## Shape fit — adequate
The shape matches a brownfield .NET Blazor front-shell framework that feeds UX, architecture, and stories. Capability-first FRs, operational success metrics, public-contract section, and named UJs for a multi-role operator/adopter/agent surface are the right genre. Existing-code references (HFC IDs, bootstrap method names, Generated Output path, Fluent v5 pin) are the right brownfield texture; sampled HFC1003/1006/1009/1065 exist in SourceTools. UJ density is not consumer-product theater.

The PRD is strained at both edges. FR-24, NFR-12/13, D-6, and D-11 are architecture and release-engineering stuffed into product requirements because there is no addendum to receive them. Operator UX is under-formalized by D-8 (“`ux-design.md` is sufficient”) even though this document’s purpose statement names UX as an audience. §5.0/§8.2 are a delivery dashboard living inside a PRD. That is not a template mismatch; it is a chain-top document doing three jobs (product contract, program status, release design) and losing done-ness on the first.

### Findings
- **[medium]** Product-contract shape is overloaded with release mechanism and underloaded with operator UX (§4, §5.7 FR-24, §6 NFR-12/13, §12 D-6/D-11, §12 D-8, §10) — Package-release readiness belongs here; RFC 3161, evaluator closures, graph-edge ceilings, and handoff hashes belong in architecture/addendum. Meanwhile the UX risk is already confessed: “UX requirements remain too compact for visual stories.” *Fix:* Keep FR-24 as publishable-artifact outcomes and evidence gates; move mechanism; if this PRD still feeds UX, require UJ/FR consequences for the remaining visual states (stale, reconnecting, FC-NIP, degraded) rather than only a pointer to `ux-design.md`.
