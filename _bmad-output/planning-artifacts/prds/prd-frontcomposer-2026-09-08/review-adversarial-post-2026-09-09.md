## Verdict

**Send back.** The update correctly withdraws the claim that protected-environment approval isolates candidate code, preserves old versus current Builds provenance, keeps UX evidence unmet, and routes the new release work through G-8. It is still not safe to use as the sole milestone-closure instrument. One Product-owned dependency decision is outside the only authoritative gate table, the release glossary still defines the rejected pre-G-8 control set as a “Governed Release,” and several gate references can be satisfied against ambiguous or stale evidence. The UX requirements are substantially better, but the addendum claims to carry matrices it does not contain and does not identify one consistent three-file UX authority.

Counts: **1 critical, 5 high, 4 medium, 1 low**.

## Findings

### Critical

- **[critical] ADV-P09-01 — The sole milestone table can close while D-13 remains explicitly unaccepted** (`prd.md:19`, `:24`, `:41`, `:556`, `:635`, `:682`, `:693`, `:706`) — Frontmatter may become `v1_readiness_milestone_reached: true` when §0.1 has no open rows, and §0.1 says it is the only authority. A literal gate operator can therefore close G-4 and every §0.1 row while the named Product co-owner has not accepted the dependency posture. *Fix:* Either make OI-4 plus D-13 provenance reconciliation an explicit G-4 pass condition, or record a dated decision that Architecture alone owns a non-gating accepted risk and remove the pending Product decision. Do not leave an unaccepted Product-owned posture outside the sole closure table.

### High

- **[high] ADV-P09-02 — The glossary still calls the rejected control set a “Governed Release”** (`prd.md:18`, `:35`, `:121-122`, `:458-470`, `:628-629`; addendum `:16-18`) — The definition requires exact-SHA dispatch, protected-environment approval, and pre-side-effect v3 classification, but omits G-8's secretless builder / pinned data-only publisher boundary. Those are precisely the controls the update says do not isolate candidate-controlled code from publication authority. Even if “Governed Release” is not intended to mean FR-24-compliant, downstream prose can now label the active unsafe topology governed by applying the glossary literally. *Fix:* Define the term using the accepted split-phase boundary and exact evaluator/attempt requirements, or retire the term until G-8 closes and refer to the current controls without the governed label.

- **[high] ADV-P09-03 — G-8 reuses A1-A5 in collision with the PRD's own assumption IDs** (`prd.md:35`, `:715`, `:721-725`; addendum `:44`; architecture validation report `:49-53`) — “Architecture resolves A1–A5” means the five findings in the 2026-09-09 GOV-1 validation report, but the PRD defines A1 and A2 as retired assumptions and A3 as the sample-host assumption; it defines no PRD A4/A5. The glossary defines `AD-n`, not this second `A-n` family. This makes a load-bearing evidence-gate condition ambiguous and breaks the otherwise preserved stable-ID discipline. *Fix:* Namespace the review findings (for example `GOV1-A1`…`GOV1-A5`) and cite the exact dated validation artifact in G-8, OI-13, and the addendum. Keep PRD assumptions in their own `A-n` family.

- **[high] ADV-P09-04 — G-4 points at stale reviews and its UX sub-gate permits a Critical finding** (`prd.md:41`, `:678`, `:718`; run folder review filenames) — `review-*-post.md` currently resolves only the three undated post-reconciliation reviews from 2026-09-08; it does not match this gate's dated `review-*-post-2026-09-09.md` outputs. The old adversarial post-review contains Critical/High findings, so the cited wildcard is either permanently failing or silently ignored in favor of files it does not name. Separately, OI-16 closes when UX validation has “no High finding,” which literally does not exclude an unresolved Critical. *Fix:* Make G-4 cite one explicit dated synthesized PRD review report (and the exact constituent review paths if needed), and require zero unresolved Critical **and** High findings in both the PRD and UX gates.

- **[high] ADV-P09-05 — G-7's implementation alternative does not dispose every security residual that OI-2 owns** (`prd.md:34`, `:381-397`, `:607`, `:683`, `:704-705`; addendum `:112-117`) — G-7 allows either an independent OI-2 disposition **or** gated-list implementation evidence. But OI-2 covers four distinct matters: static resource-catalog disclosure, the unregistered-resource SDK error, the `tools/list` credential-validity signal, and host authentication. Gating `resources/list`/`resources/read` can remove the resource disclosure, but it does not decide whether the still-disclosed `tools/list` signal is acceptable; tests establish behavior, not risk acceptance. The `or` branch therefore permits G-7 closure without an independent disposition of residual behavior. *Fix:* Require an independent security disposition after implementation for every residual that remains observable. Treat gated-list work as replacing only the resource-specific acceptance, not the whole OI-2 decision, unless its evidence demonstrates that every listed residual was eliminated.

- **[high] ADV-P09-06 — G-3 can waive its named external approver by an owner declaration with no authority rule** (`prd.md:32`, `:681`; reconciliation validation extract `:44`) — G-3 says the record is signed by the EventStore maintainer role “or explicitly declares the role is FrontComposer-owned,” while the owner column and D-12 still name the EventStore maintainer as approver. The text does not say who may reclassify that role, so a FrontComposer-authored record can apparently declare away the external signature that the same row requires. This is not a stable approval boundary. *Fix:* Choose one route: require the EventStore-maintainer signature, or record a separate dated Product/Architecture ownership decision that makes the approval FrontComposer-owned and then remove EventStore from the gate's required owners. The migration evidence and provenance reconciliation remain mandatory either way.
