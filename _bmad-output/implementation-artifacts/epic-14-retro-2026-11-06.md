### Defects and verification gaps

**F-1: MCP lifecycle snapshots are readable across tenants and users (AC 14.2 #4). Lenses: all three, independently. Instance: fix now (A1).**
- *Cause.* `LifecycleEntry` stores only `Descriptor`, `CorrelationId` and `MessageId` (`FrontComposerMcpLifecycleStore.cs:307–322`), and the store is a process-wide singleton (`FrontComposerMcpServiceCollectionExtensions.cs:43`). `ReadCoreAsync` only re-checks that the *current* caller can still see the same tool (`FrontComposerMcpLifecycleTracker.cs:46–61`).
- *Reproduced.* The probe shows `tenant-a/user-b` and `tenant-b/user-b` both receive `tenant-a/user-a`'s snapshot (Behavior verification). The snapshot carries state history and the terminal outcome, including `entityId` and `message` (`McpLifecycleModels.cs:68–89`).
- *Handles are guessable.* The singleton `FrontComposerMcpUlidFactory` increments within the same millisecond, shared across every caller (`FrontComposerMcpUlidFactory.cs`; registration `FrontComposerMcpServiceCollectionExtensions.cs:51`). The invoker draws two consecutive ULIDs per command (`FrontComposerMcpCommandInvoker.cs:402–410`), so handles issued in the same millisecond are adjacent values.
- *Why the evidence missed it.* The packet cited "cross-scope lifecycle tests". Those tests keep one identity and toggle visibility (`CommandLifecycleTests.cs:228–275`; `McpCommandToolAdapterTests.cs:385–449`), and the named audit has no lifecycle step.
- *Prevention.* An AC naming two principals needs a test with two principals; reuse claims must be checked against what the reused test actually varies.

**F-2: The framework's "requires authorization" guarantee is silently substitutable. Lenses: adversarial, verification-gap. Instance: fix now (A2).**
- *Cause.* `MapMcp(route).RequireAuthorization()` (`…RouteBuilderExtensions.cs:34`) adds an empty `[Authorize]`. Once any `AuthorizationPolicy` object is appended, ASP.NET stops applying the default authenticated-user policy.
- *Reproduced.* An anonymous POST to the framework-only mapping gets **401**; the same mapping plus any host policy gets **200** (`scratchpad/authz-probe`).
- *In-repo reliance.* The Counter `Test` host relies on exactly this (`samples/Counter/Counter.Web/Program.cs:233–236`). At HEAD, the anonymous `mcp-fail-closed-security.spec.ts:38` passes on Chromium and Firefox (Quality 42210402990).
- *Why the test misses it.* The governance assertion checks only that `IAuthorizeData` is present and `IAllowAnonymous` is absent (`McpSecurityGovernanceTests.cs:96–97`), not the effective policy.
- *Contract.* PRD `prd.md:403` and `package-and-hosting.md:40` state that authorization is required on every mapped endpoint.
- *Prevention.* Assert effective outcomes, not metadata shapes. This matches the E15 lesson AG-7, "guard outcomes".

**F-3: A breaking host-composition change shipped as `fix:` in v4.6.0, and it disabled the built-in API-key path. Lenses: all three. Instance: fix now (A3).**
- *How it shipped.* v4.6.0 (2026-10-05) lists `e566665` under Bug Fixes with no breaking-change note (`gh release view v4.6.0`). `CHANGELOG.md` stops at 4.0.1, and `docs/` never mentions `ApiKeys`.
- *What breaks.* Three things: startup now throws outside Development for `AllowAll*` gates; `RequireAuthorization()` is now enforced; and `FrontComposerMcpOptions.ApiKeys` is unreachable. The API key is matched inside the handler (`HttpFrontComposerMcpAgentContextAccessor.cs:82–96`), which runs only after the authorization middleware, so an API-key-only host gets 401 unless it registers its own ASP.NET scheme.
- *Coverage.* No test pins the API-key-only behavior; `AuthContextAccessorTests` calls the accessor directly, with no middleware.
- *Workaround in the sample.* The in-repo repair duplicated credential validation in `CounterMcpSampleAuthenticationHandler.cs:25`, using an ordinal `string.Equals` rather than the store's matcher.
- *Prevention.* Treat host-composition changes as breaking: Conventional Commits `!`/`BREAKING CHANGE`, plus a migration note. The same gap recurs in E15R-AI-5 (the FcShellOptions startup-validation change).

**F-4: The epic broke the in-repo MCP host, and the break crossed a story boundary unnoticed. Lenses: all three. Instance: already resolved by `b7384b97`; ledger hygiene (A6). Prevention: A7.**
- *What broke.* At `1f33be41`, Counter enabled MCP for `Development || Test` with `AllowAll*` gates and no ASP.NET authentication. Under `Test` (the Playwright environment), mapping threw at startup; under `Development`, every request faced the new authorization requirement.
- *Who saw it.* Story 13.1's code review saw both problems **the same day** and deferred them as "intervening MCP work" (`deferred-work.md:9869,9873`).
